# Підключення до MCU Debug Interface (C2) через Arduino

Status: reference (how-to)
Date: 2026-07-16
Пов'язані документи: [firmware_hardware.spike.md](firmware_hardware.spike.md),
[firmware_update_method.spike.md](firmware_update_method.spike.md) (§5, §8),
[ofw_mask_cryptanalysis.spike.md](ofw_mask_cryptanalysis.spike.md).

## 1. Що це за інтерфейс

На платі осцилографа стоїть мікроконтролер **Silicon Labs C8051F34x** (ядро 8051). Гребінка
з написом **«MCU Debug Interface»** — це **C2 (Silicon Labs 2-Wire Interface)**, фірмовий
2-провідний інтерфейс налагодження/програмування. Через нього можна прочитати ID чипа,
записати/стерти flash і (якщо не заблоковано) вичитати flash.

Arduino цілком здатний бути дешевим C2-програматором: обидві лінії C2 тактуються програмно
(bit-bang), готові скетчі існують (див. §5). Це саме той «C2-адаптер», про який ідеться в
`firmware_update_method.spike.md` як про **Path A** (вичитати одну сторінку flash → отримати
known-plaintext → відновити keystream → розшифрувати `.ofw`).

> 🔒 **СТАТУС БЛОКУВАННЯ — ВЕРИФІКОВАНО (2026-07-17): readback flash ЗАБЛОКОВАНО.**
> Перевірено на живому залізі через **Raspberry Pi 4B + fast-C C2** (`firmware/rpi_c2/c2_rpi.c`, §9):
> C2 повністю працює (Device ID `0x0C`, FPCTL-halt тримається), але **будь-яке Block Read flash
> → фіксована помилка `st2=0x03` + device reset** (сигнатура flash-security). **Простий C2-дамп
> flash НЕМОЖЛИВИЙ; Path A (known-plaintext) закрито без voltage-glitch.** Деталі — §9.
>
> _(Історія нижче — як дійшли до цього; лишено для контексту методики.)_ Можливі два результати:
> - **flash НЕ заблоковано** → можна одразу вичитати сторінку flash = отримати known-plaintext
>   для відновлення keystream (Path A, `ofw_mask_cryptanalysis.spike.md`) — найкоротший шлях;
> - **flash заблоковано** → read device ID працює, але вичитування flash блокується; mass-erase
>   стирає і bootloader (незворотно, відновлює лише виробник); обхід — лише voltage-glitch
>   (`C8051F34x_Glitch`, §6).
>
> У будь-якому разі Arduino-підключення корисне: підтвердити точний суб-номер F34x за device ID,
> **перевірити гіпотезу про блокування**, а далі — або читати flash, або йти в glitch/Path C.

## 2. Розпіновка плати → сигнали C2

Точки для пайки на платі та їх відповідність сигналам C2:

| Точка на платі | Сигнал C2 | Пояснення |
|----------------|-----------|-----------|
| **C2Dat** | **C2D** (data) | Двонаправлена лінія даних C2 |
| **-RFS** (він же `-RES` / `/RST`) | **C2CK** (clock) | Такт C2. На C8051F34x лінія C2CK **суміщена з виводом скидання** `/RST`, тому на платі підписана як reset |
| **+3V3** | VDD (3.3 В) | Живлення/опорна напруга ядра (3.3 В) |
| **GND** | GND | Спільна земля |

Тобто пара, що несе власне C2, — це **C2Dat (=C2D)** і **-RFS (=C2CK)**; `+3V3` і `GND`
задають рівні напруги та спільну землю.

## 3. ⚠️ Рівні напруги — головна пересторога

C8051F34x живиться від **3.3 В**, і лінії C2 працюють у 3.3-вольтовій логіці. Класичні Arduino
(**Uno / Nano / Mega — 5 В логіка**) під'єднувати напряму **ризиковано**: можна пошкодити
мікроконтролер або отримати нестабільний зв'язок. Оберіть один із варіантів:

- **Найкраще — 3.3 В Arduino.** Плата з 3.3-вольтовим I/O: *Arduino Pro Mini 3.3 V / 8 MHz*,
  *Arduino Zero/MKR*, або будь-яка ESP/STM-плата. Тоді рівні збігаються, зайвих деталей нема.
- **Level shifter.** Двонаправлений перетворювач рівнів на MOSFET (модуль на BSS138) на лінії
  **C2D** і **C2CK**: низька сторона — до +3V3 плати, висока — до 5 В Arduino.
- **Резистори послідовно** (грубий, але робочий для bit-bang C2): ~1–4.7 кОм у розрив кожної
  сигнальної лінії. Обмежує струм, але не є повноцінним зсувом рівня — застосовувати як тимчасове
  рішення.

> Примітка: у частини чипів Silicon Labs (напр. Si10xx) виводи C2 заявлені як 5V-tolerant, тоді
> як VDD — ні. Для C8051F34x **безпечне припущення — 3.3 В логіка**; якщо хочете підключати 5 В
> напряму, спершу звірте абсолютні максимуми у datasheet саме вашого суб-номера.

## 3a. Вибір із наявного заліза: Arduino Due R3 vs Uno

У наявності **Arduino Due R3** і **Arduino Uno**. Для C2-підключення до 3.3-вольтового C8051F34x
вони кардинально різні:

| Критерій | **Arduino Due R3** | **Arduino Uno** |
|---|---|---|
| Логіка I/O | **3.3 В** (ARM SAM3X8E) | 5 В (AVR ATmega328P) |
| Level shifter потрібен? | **Ні** — рівні збігаються, пряме з'єднання | **Так, обов'язково** (5 В→3.3 В на C2D/C2CK) |
| Ризик для чипа | мінімальний | високий без зсуву рівнів |
| Готовий скетч x893 `C2_Flash.pde` | **Ні** — він під AVR (прямий PortD), на ARM не працює | **Так**, запускається як є (C2CK=D5, C2D=D6) |
| 5V-tolerant входи | **Ні** (не подавати 5 В на Due!) | так |

**Рекомендація:**

- **Пріоритет — Arduino Due** (безпечніше для рідкісного C8051F34x): рівні 3.3 В збігаються, зсув
  рівнів не потрібен, ризик спалити чип мінімальний. **Ціна** — готовий AVR-скетч треба
  **адаптувати під Due**: переписати дві низькорівневі bit-bang примітиви (керування C2CK і
  читання/запис C2D) через `digitalWrite`/`digitalRead`/`pinMode` або, надійніше, через прямі
  PIO-регістри SAM3X. C2 не має мінімальної тактової частоти, тож повільний bit-bang прийнятний.
  ⚠️ Один нюанс таймінгу: START — це **короткий** негативний строб C2CK; оскільки C2CK суміщений з
  `/RST`, **надто довге** утримання C2CK у low спричинить скидання чипа. На Due `digitalWrite`
  (тактова 84 МГц) досить швидкий, але для стабільності краще прямі PIO-регістри.

- **Альтернатива — Arduino Uno**, якщо хочете **готове ПЗ без переписування**: заливаєте
  `C2_Flash.pde` як є, але **обов'язково** ставите двонаправлений level shifter (модуль на BSS138)
  на C2D і C2CK, низька сторона — до `+3V3` плати. Без зсуву рівнів 5 В подавати на чип **не можна**.
  Врахуйте: вивід 3.3 В на Uno слабкий (~50 mA від бортового регулятора) — на живлення цілі не
  розраховуйте, лише як опору для level shifter.

**Підсумок:** Due = безпека за ціну адаптації скетча; Uno = готовий скетч за ціну обов'язкового
level shifter. Для збереження рідкісного залізяччя перевага — **Due**.

## 4. Схема підключення

> **Про позначення «D5»/«D6».** Це умовна назва в коді (D = *Digital pin*), а не напис на платі:
> на шовкографії Arduino надруковано **просто число** (`5`, `6`, для ШІМ — `~5`/`~6`) у ряду
> **DIGITAL**. «D5/D6» — це **дефолт лише AVR-скетча x893 на Uno** (там вони жорстко = біти PortD).
> На **Due** ви **не прив'язані** до 5/6: обираєте будь-які два з цифрових пінів `0–53` (крім `0`/`1`
> — це Serial) і **прописуєте їхні номери у своєму скетчі**. Головне — номер у коді має збігатися з
> фізичним піном, куди заведено провід.

Таблиця з'єднань. Піни залежать від плати (див. §3a): на **Uno** з готовим скетчем x893 —
пін `5`=C2CK, пін `6`=C2D (через level shifter!); на **Due** — будь-які два GPIO (напр. `22`=C2CK,
`24`=C2D), які ви пропишете в адаптованому скетчі (пряме з'єднання, без зсуву рівнів):

| Плата осцилографа | Зв'язок | Arduino (пін = число на шовкографії) |
|-------------------|:-------:|--------------------------------------|
| C2Dat (C2D)       | Due: прямо · Uno: через level shifter | Due: пін `24` · Uno: пін `6` |
| -RFS (C2CK)       | Due: прямо · Uno: через level shifter | Due: пін `22` · Uno: пін `5` |
| GND               | прямо   | GND (спільна — обов'язково!) |
| +3V3              | опора   | опорна 3.3 В для level shifter (Uno) або живлення цілі — див. §4.1 |

(Номери пінів Due — приклад; підійдуть будь-які вільні `2–53`, аби збігалися зі скетчем.)

```
   Плата осцилографа        Arduino Due (3.3 В — ПРЯМО, без level shifter)
   (C8051F34x, 3.3 В)
   ┌────────────────┐                        ┌──────────────────┐
   │  C2Dat (C2D) ●──┼────────────────────────┼── пін 24  (C2D)  │
   │  -RFS (C2CK) ●──┼────────────────────────┼── пін 22  (C2CK) │
   │  GND         ●──┼────────────────────────┼── GND            │
   │  +3V3        ●──┼──(не з'єднувати, якщо   │  (живлення Due — │
   │                 │   осцилограф живиться    │   свій USB)      │
   │                 │   сам; див. §4.1)        │                  │
   └────────────────┘                        └──────────────────┘

   Для Uno (5 В) — ті самі лінії, але C2D/C2CK через двонаправлений
   level shifter (BSS138): низька сторона → +3V3 плати, висока → 5V Uno;
   піни Uno: 6=C2D, 5=C2CK.
```

### 4.1 Живлення: важливо не «зіштовхнути» два джерела

- Якщо осцилограф уже живиться **сам** (від свого USB/БЖ) — **НЕ** подавайте на його `+3V3`
  живлення з Arduino. З'єднайте лише **GND ↔ GND** і сигнали (через зсув рівнів), а `+3V3` плати
  використовуйте тільки як **опорну** для високої/низької сторони level shifter. Подача зустрічного
  живлення на увімкнену плату може її пошкодити.
- Якщо живите ціль **від Arduino** — тоді осцилограф має бути **знеструмлений** з боку USB, а
  `+3V3` Arduino подається на `+3V3` плати. Для цілої плати осцилографа це небажано (велике
  споживання, аналогова частина); практичніше живити плату штатно та ділити лише землю + сигнали.

**Рекомендація:** живіть осцилограф штатно (його USB), Arduino — своїм USB, обов'язково
об'єднайте **GND**, сигнали заводьте через зсув рівнів.

## 4.2. ⚠️ Уточнена схема Uno (емпірично, 2026-07-16) — резистор **1.2 кΩ**, НЕ 3.3к

Загальні поради вище (§3, §7b: «2.2–4.7к» / «3.3к») **уточнено живим тестом**: на цьому стенді
**3.3к клок не доходив** (RC із внутрішнім pull-up /RST 150к + ємність завалює фронти), а **1.2 кΩ
працює** (підтверджено: hold C2CK low → осцилограф мертвий, тобто клок реально керує /RST). Тож для
серії резисторів **використовуй 1.2 кΩ**.

| Точка плати | Сигнал | Uno пін (жорстко в x893) | В лінії |
|---|---|---|---|
| **C2Dat** | C2D (=P2.0) | **D6** (PORTD6) | **1.2 кΩ послідовно** |
| **-RFS**  | C2CK (=/RST) | **D5** (PORTD5) | **1.2 кΩ послідовно** |
| **GND**   | GND | **GND** | прямо (без резистора) |
| **+3V3**  | VDD | — | **НЕ з'єднувати** (scope живиться сам) |

```
  Плата (C8051F41x, 3.3В)                     Arduino Uno (5В)
   C2Dat (C2D=P2.0) ●──[1.2kΩ]────────────────● D6  (PORTD6)
   -RFS  (C2CK=/RST)●──[1.2kΩ]────────────────● D5  (PORTD5)
   GND              ●───────────────────────── ● GND (спільна, ПРЯМО)
   +3V3             ●──✗ не тягнути               (Uno — свій USB)
```

- **Струм безпечний:** через ESD-діоди P2.0/RST при 1.2к ≈ (5−3.6)/1200 ≈ **1.2 мА**.
- **Пін-мапа жорстка:** D5=C2CK, D6=C2D (= біти PORTD5/6 у `arduino_c2_uno.ino`); змінювати лише
  разом із правкою скетча. Скетч навмисно сповільнює такт (LOW 3µs / HIGH 4µs) під RC.
- **Uno = CH340:** serial читати лише з `dtr=False,rts=False` (інакше DTR тримає плату в reset).
- **Uno bring-up — покроковий діагноз (2026-07-16, живе залізо). Ізольовано до C2D-READ.**
  Метод перевірки лінка **без freeze**: `arduino_hold_reset` тримає C2CK(/RST) low → якщо
  осцилограф зникає з OBEX (`scripts/test_connect.py`), лінк+GND живі; reset самовідновний.
  - **C2CK + GND:** спершу були зламані (утримання /RST не вбивало scope) → після перепайки
    **OK** (scope мертвіє на hold-low). Причина була в **-RFS/GND-лінії, не C2D**.
  - **C2D WRITE:** **працює** — FPCTL-halt (0x02,0x04,0x01 через C2D) реально халтить ядро
    (scope замерзає; знімається лише power-cycle). Тобто провід C2D і запис у нього — ОК.
  - **C2D READ:** **зламаний** — Device ID Data Read = `0xFF`, Address Read = `0xFE` (bit0 low,
    решта stuck-high), **незалежно від такту (3/4…60/90µs) і навіть при halt** (тобто не firmware-
    контенція P2.0, а електрика). Пін D6 справний (self-test low→0/high→1). Отже: **єдиний блокер —
    напрямок читання C2D** (3.3В→5В через послідовний 1.2к біасить у high).
  - **Фікс (найнадійніше):** **BSS138 level shifter на C2D** (двонаправлена лінія). C2CK лишати на
    1.2к — він **однонаправлений** (Uno→ціль), запис працює. Швидка безкоштовна перевірка перед
    шифтером: **зняти будь-який pull-up з C2D** (він біасить читання в high, а запис ще проходить);
    можна також спробувати **менший послідовний R на C2D (~680Ω)**, щоб ціль певніше тягла D6 в низ.
  - Перевірка після фіксу (non-halt, без freeze): `arduino_c2_uno_diag` auto-loop → **Device ID
    має стати `0x0C`**. Лише тоді Block Read (halt) має сенс — і тоді робочий x893 Address Read
    дасть коректне OutReady-опитування → реальний дамп.

## 5. Програмне забезпечення

Готові C2-програматори на Arduino (усі — bit-bang C2 за AN127):

- **x893/C2.Flash** — <https://github.com/x893/C2.Flash> — саме цей проєкт згаданий у наших
  спайках. Містить скетч **`C2_Flash.pde`** для AVR-Arduino; за замовчуванням **C2CK = D5,
  C2D = D6**. Хост-утиліта **`SendC2.exe`** (командний рядок) / GUI `C2.Flash.exe` (.NET 2.0)
  заливає hex у ціль. Реалізує офіційний протокол Silicon Labs **AN127**.
- **merbanan/c2gen** — <https://github.com/merbanan/c2gen> — Arduino-програматор під форк
  **`c2tool`** (зручно на Linux; читання device ID, read/write/erase flash з CLI).
- **conorpp/efm8-arduino-programmer**, **iainguilliard/c2prog** — альтернативні скетчі C2 на
  Arduino (орієнтовані на EFM8/SiK, але протокол C2 той самий).

Специфікація протоколу: **AN127 «Flash Programming via the C2 Interface»**
(<https://www.silabs.com/documents/public/application-notes/AN127.pdf>). C2 — це START (негативний
строб C2CK) → 2-бітне поле INS → адреса/дані (LSB first) через регістри Address/Data; після будь-якого
reset регістр адреси = 0 і вказує на **Device ID** — тому ID читається одразу після ініціалізації.

## 6. Спецвипадок: ЯКЩО readback виявиться заблокованим

Це сценарій **на випадок, якщо** перевірка §7 крок 5 покаже встановлений біт захисту (наразі
не підтверджено). Тоді звичайний C2-дамп не спрацює, і актуальним стає матеріал —
**debug-silicon/C8051F34x_Glitch** (<https://github.com/debug-silicon/C8051F34x_Glitch>):
обхід біта захисту через **voltage glitch** під час C2-команди Block Read. Там використано
BluePill (STM32F103) як DIY C2-дебагер (**C2CK=PB3, C2D=PB4**) + ChipWhisperer-Lite + доопрацювання
плати (зняти регулятор, шунт 50 Ω по VDD, зовнішні 3.3 В). Не руйнівний — flash і bootloader
зберігаються. Це важче за просте Arduino-читання, але єдиний шлях дістати known-plaintext при
locked flash. Деталі та застереження — у `firmware_update_method.spike.md` §8.

## 7. Порядок першого підключення (checklist)

1. Знеструмити все. Спаяти/під'єднати проводи: C2Dat→C2D, -RFS→C2CK, GND↔GND (через зсув рівнів,
   якщо Arduino 5 В).
2. Обрати схему живлення за §4.1 (найпростіше: осцилограф — штатно, ділимо лише GND + сигнали).
3. Прошити Arduino скетчем C2-програматора (§5), звірити піни C2CK/C2D із розводкою.
4. Подати живлення, запустити хост-утиліту, виконати **Read Device ID / Revision**.
   Успішне читання ID = зв'язок C2 є; заодно фіксуємо точний суб-номер C8051F34x.
5. **Ключова перевірка гіпотези:** прочитати стан **security/lock byte** (спроба Block Read
   сторінки flash). Це і є той тест, якого бракує — блокування наразі лише припущення.
   - flash **не** заблоковано → одразу вичитати сторінку = «одна known-plaintext сторінка» для
     відновлення keystream (див. `ofw_mask_cryptanalysis.spike.md`), Path A відкрито;
   - flash заблоковано → device ID читається, flash — ні; переходити до glitch-сценарію (§6).

Стенд: **Arduino Due** (3.3 В, пряме підключення), скетч `firmware/arduino_c2/arduino_c2.ino`

- ✅ ** Core halt через FPCTL** (`0x02→0x01`) підтверджено (WAIT-ack є) → Flash-інтерфейс досяжний.

- ⚠️ **Зв'язок маргінальний:** Device ID читається як `0x0C` замість еталонного **`0x0F`**

  digitalWrite/register-I/O + різні затримки; поведінка timing-sensitive → апаратна природа.

**Конфігурація стенду:** осцилограф на власному живленні; **+3V3 між платами НЕ зʼєднано**
(правильно — не тягнути на Due, щоб не звести два джерела). Спільні лише **GND + C2D + C2CK**.

**Спроба PI-команд (Block Read / Get Derivative) — 2026-07-16, ПІДСУМОК:**
- Виправлено на FPDAT@**0xB4** (C8051F41x). Реалізовано і з опитуванням InBusy/OutReady через
  Address Read, і без (на WAIT-полях Data Read/Write) + різні тайминги, з pull-up і без,
  register-I/O і digitalWrite.
- **Одиночне Data Read (з WAIT) — надійне** (Device ID 0x0C, Rev 0x02 стабільні, чип ідентифіковано).
- **Address Read (без WAIT) — НЕ надійний**: round-trip AR (write 0xA5 → read) = FAIL (0x00/зсуви),
  bit0=OutReady не зчитується через turnaround. Оскільки AN127 вимагає опитувати InBusy/OutReady
  саме Address Read'ом, **багатокрокова PI-послідовність (Block Read) десинхронізується** →
  повертає то нулі, то 0x08 — **артефакти, а не справжня відповідь про блокування**.
- **Висновок:** цей hand-rolled bit-bang на Due годиться лише для одиночних read'ів (ідентифікація
  чипа). Для дампу/lock-перевірки потрібна **перевірена реалізація** — див. нижче.

**Аудит субагента на чистому контексті (2026-07-16) — застосовано, PI все одно не працює:**
Незалежний review проти AN127 знайшов **реальні баги** (виправлено): (1) у Block Read був **зайвий
status-read** (off-by-one, що з'їдав перший байт даних — Block Read має лише ОДИН статус 0x0D);
(2) під час START/STOP драйвер C2D не відпускався (§1.5.x); (3) `dIn()` без pull-up лишав C2D
плаваючим у turnaround → Address Read (без WAIT) читав першими бітами сміття. Підтверджено, що
**0x0C — правильний ID F41x** (Data Read не помилявся). Після виправлень + 3-ключовий halt
(0x02,0x04,0x01, де 0x04=halt core): Device ID/Rev читаються стабільно, але **PI не відповідає**
(статус Block Read ≠ 0x0D, дані `00 E0 E0…`, Get Derivative 0xFF). PI-enable/core-halt та статус-
опитування не «беруться» надійно на bit-bang (Address Read зламаний turnaround'ом; WAIT-handshake з
pull-up дає хибні ack). **Одиночні C2-read працюють; багатокрокова PI — ні. Потрібна перевірена
реалізація з правильним залізом.**

**Осцилограф перевірено окремо (2026-07-16):** живий і робочий — OBEX-handshake OK, VNM=Uosc,

**Що зробити для чистого читання (перед перевіркою lock-біта / читанням flash):**

### ⚠️ ВИПРАВЛЕННЯ ЧИПА (2026-07-16): це **C8051F41x**, НЕ F34x

Читання C2 Device ID = **0x0C** відповідає **C8051F41x** (datasheet: "returns the 8-bit device ID:
0x0C (C8051F41x)"), а НЕ C8051F34x (той має 0x0F). Тобто ідентифікація в
`firmware_hardware.spike.md`/`firmware_update_method.spike.md` (F34x) **помилкова** — насправді чип
**C8051F410/411** (прошивка 30КБ → 32КБ flash; F412/413 мають лише 16КБ). Наслідки:
- **C8051F41x НЕ має USB** (це MCU з smaRTClock + 12-біт ADC) → USB на платі це **окремий міст
  CP210x** (пояснює `10c4:840e` і драйвер `cp210x`; MCU спілкується через UART).
- **FPDAT для F41x = 0xB4** (а не 0xAD як у F34x) — саме тому Block Read спочатку давав сміття.
- Voltage-glitch репозиторій `C8051F34x_Glitch` — під F340; **для F41x не застосовний як є**.

**Авторитетна C2-мапа для C8051F41x** (datasheet §26 + AN127):

| C2 addr | Регістр | Призначення |
|---|---|---|
| 0x00 | DEVICEID | Device ID = **0x0C** ✓ (наш read) |
| 0x01 | REVID | Revision (наш read 0x02 = пізніша ревізія) |
| 0x02 | FPCTL | halt/enable: записати **0x02, 0x01** після reset |
| **0xB4** | FPDAT | команди flash; **Block Read = 0x06** |

Наступний крок (після pull-up і чистого `0x0F`): через FPDAT видати Block Read однієї сторінки →
перевірити, чи readback заблоковано (це і є верифікація гіпотези з §1). Якщо не заблоковано —
маємо known-plaintext сторінку для відновлення keystream (Path A, `ofw_mask_cryptanalysis.spike.md`).

## 7b. ⚠️ Чи 5V-толерантні піни C2 у C8051F41x? — НІ (datasheet-перевірено)

Питання виникло при спробі підключити 5В Uno напряму без level shifter. Відповідь з datasheet
C8051F41x (Absolute Maximum Ratings + §26):
- **C2CK = /RST, C2D = P2.0** (§26: «C2 interface can borrow C2CK (/RST) and C2D (P2.0)»).
- **Лише Port 0 піни 5V-толерантні** (до 5.5В). **Усі інші, включно з P2.0 (C2D), — max VIO+0.3 ≈ 3.6В.**
- 5.25В стосується **живлення** (VREGIN + внутрішній LDO), НЕ пінів C2.
- **Висновок: 5В Uno напряму на C2 — НЕ можна** (P2.0 не 5V-толерантний → ризик пошкодження).

**Варіанти з Uno без level shifter:**
- **Послідовні резистори ~2.2–4.7 кОм** у лініях C2D і C2CK — струм у не-5V-толерантний пін
  обмежується через вбудовані ESD-діоди чипа (≈0.5мА при 2.2к). Широко застосовується для
  5В↔3.3В C2/JTAG; не спец-чисто, але низький ризик. Найдешевший шлях без шифтера.
- Або дешевий MOSFET level shifter (BSS138).

**Найкраще для напруги — Arduino Due (3.3В): C2 напряму, безпечно, без жодних резисторів.** Проблема
Due — не напруга, а що register-PIO доступ на цьому екземплярі не працює (PIO_ODR не відпускає пін →
усе 0x00), а pinMode/digitalWrite надто повільні/джитерні для Address Read (turnaround без WAIT).
Тобто: Due безпечний але не тягне Address Read; Uno тягне (швидкий AVR-порт, x893) але потребує
резисторів/шифтера через 5В.

## 7d. C2 command survey — робота решти команд (2026-07-16, Due, opus-4-8)

Мета сесії: перевірити роботу **решти C2-команд** (поза Device ID) на живому Due і скласти звіт;
тверде обмеження — **не стерти прошивку**. Стенд: тільки Due (пряме 3.3В), осцилограф на своєму

serial-командою). Erase-безпека: у **жодному** скетчі проєкту немає опкодів `0x03`/`0x07`/`0x08`;
єдина FPDAT-команда будь-де — `0x06` (Block Read, read-only).

**Матриця C2-інструкцій (перевірено на залізі):**

| Інструкція (INS) | Halt? | Результат | Примітка |
|---|---|---|---|
| Data Read (00) + WAIT | ні | ✅ **надійно** | Device ID `0x0C` / Rev `0x02` стабільно. Самосинхр. через WAIT |
| Address Write (11) | ні | ✅ надійно | host-driven, без turnaround |
| Data Write (01) + WAIT | так* | ✅ працює | приймається (див. FPCTL/FPDAT нижче) |
| **Address Read (10)** | ні | ❌ **ненадійний** | свіп turnaround(0/1/2)×pull-up: `0xA5→00/80/C0`, `0x3C→FF/F0/F8`. Немає WAIT-хендшейку + повільний/джитерний bit-bang + плаваючий turnaround |

> **⚠️ Уточнення (AN127 §1.2.1, кешовано `.dev_flow/cache/AN127.pdf`):** Address Read **НЕ повертає
> записану адресу** — він повертає **8-бітний статус PI**: bit7 `FLBusy`, bit6 `EError`, bit1
> `InBusy`, bit0 `OutReady`. Тому давня перевірка «write 0xA5 → read 0xA5» (з x893/Uno-скетча) —
> **хибна для цього чипа** (насправді має вертати статус, а в idle ≈`0x00`). Незалежно від цього:
> результати мого свіпу **різняться** за turnaround-лічильником і за probe (для читання статусу вони
> мали б бути **сталими**) → кадр AR **misreads** біти, які драйвить ціль. AN127 вимагає опитувати
> `InBusy` (після кожного запису у FPDAT) і `OutReady` (перед кожним читанням FPDAT) саме через
> Address Read — тому непрацюючий AR і блокує стрімінг даних FPDAT (нижче). Функційно (див. Block
> Read) висновок незмінний. **TODO next session:** прибрати `rt==0xA5`-перевірку в
> `arduino_c2_uno.ino` — вона дасть хибний FAIL навіть на робочому AR.

**FPDAT-команди (потребують FPCTL-halt → осцилограф зависає до power-cycle; усі read-only):**

| FPDAT cmd | Результат | Оцінка |
|---|---|---|
| `c2Connect` (FPCTL 0x02,0x04,0x01) | `OK` | halt ядра стається |
| Get Version (0x01) | `0x0D` | =status echo, не версія (див. нижче) |
| Get Derivative (0x02) | `0x0D` | те саме значення, що й 0x01 → підозріло |
| **Block Read (0x06)** | `status=0x0D` ✓, дані `03 03 … ×16` | **command handshake ПРАЦЮЄ**, але дані — артефакт |

**Повний набір команд C2 (AN127 Table 3.1, кешовано `.dev_flow/cache/AN127.pdf`).** На рівні шини є
лише **4 інструкції** (2-біт INS: Data Read `00`, Data Write `01`, Address Read `10`, Address Write
`11`) + C2-reset (довгий low на C2CK). «Команди» — це коди, що пишуться у **FPDAT** (@0xB4) після
enable PI (`FPCTL`←0x02,0x04,0x01). Статус-відповідь `0x0D` = «command OK».

| Код | Команда | Тип | Стирає flash? | Перевірено цю сесію |
|---|---|---|---|---|
| `0x01` | Get Version | read | ні | так (=0x0D артефакт) |
| `0x02` | Get Derivative | read | ні | так (=0x0D артефакт) |
| `0x03` | **Device Erase** (mass) | **erase** | **ТАК — стирає й bootloader!** | **ні (заборонено)** |
| `0x06` | Block Read | read flash | ні | так (handshake ✓, дані ✗) |
| `0x07` | **Block Write** | **write flash** | ні (пише) | **ні (заборонено)** |
| `0x08` | **Page Erase** | **erase** | **ТАК (сторінку)** | **ні (заборонено)** |
| `0x09` | Direct Read | read (SFR/direct RAM) | ні | ✅ **ВІДХИЛЕНО (0x03) — не підтримується F41x** |
| `0x0A` | Direct Write | write (SFR/direct RAM) | ні (RAM) | ✅ **ВІДХИЛЕНО (0x03)** |
| `0x0B` | Indirect Read | read (XRAM/idata via ptr) | ні | ✅ **ВІДХИЛЕНО (0x03)** |
| `0x0C` | Indirect Write | write (XRAM/idata via ptr) | ні (RAM) | ✅ **ВІДХИЛЕНО (0x03)** |

**Command-acceptance sweep (2026-07-16, Due, halt): які коди PI взагалі приймає.** Метод: reconnect →
надіслати лише байт команди → прочитати command-status (0x0D=accepted / 0x03=rejected); **без**
аргументів/arming → жодна операція не завершується (erase-safe; 0x03/0x07/0x08 у зонді **не** слалися).

| cmd | status | | cmd | status |
|---|---|---|---|---|
| `0x01` Get Version | `0x0D` accepted | | `0x09` Direct Read | `0x03` **rejected** |
| `0x02` Get Derivative | `0x0D` accepted | | `0x0A` Direct Write | `0x03` **rejected** |
| `0x05` (undefined) | `0x0D` accepted | | `0x0B` Indirect Read | `0x03` **rejected** |
| `0x06` Block Read | `0x0D` accepted | | `0x0C` Indirect Write | `0x03` **rejected** |
| | | | `0xFF` (undefined) | `0x03` **rejected** |

**Висновок (hardware-verified):** PI цього C8051F41x приймає **лише низькі коди (≤ ~0x08 — набір
flash-програмування)** і **відхиляє ≥ 0x09**. Тобто **Direct/Indirect Read/Write (0x09–0x0C) НЕ
реалізовані** у PI-ROM F41x — це розширені debug-команди старших/більших пристроїв (їх дає повний
дебаг-адаптер EC2/EC3, не мінімальний flash-PI цього чипа). Це **не** артефакт Address-Read:
відмова читається чисто на етапі command-status (accepted-команди дають стабільний 0x0D). Заувага:
`0x05` (недокументований) теж приймається (0x0D) — межа прийняття ~0x08, не точно «лише документовані».
Наслідок для erase-безпеки: небезпечні `0x03/0x07/0x08` — у прийнятному діапазоні (тобто «живі», якби
надіслати з аргументами), тому їх і не чіпаємо.

- **Read-only й безпечні** (не чіпають flash): `0x01, 0x02, 0x06, 0x09, 0x0B`.
- **Небезпечні** (стирання/запис flash — у цій задачі **заборонені**): `0x03, 0x07, 0x08`.
- `0x09/0x0B` (Direct/Indirect **Read**) — читання RAM/SFR ядра для дебагу; не дають flash, але корисні
  для інспекції стану. Усі FPDAT-команди йдуть через той самий InBusy/OutReady-handshake → впираються
  у той самий Address-Read-блокер.
- EPROM-варіанти (EPCTL/EPDAT/EPADDR) — **не стосуються** C8051F41x (це flash-, не EPROM-пристрій).

**Ключові висновки:**
1. **AR-free PI command handshake ПРАЦЮЄ** — прибравши стару InBusy/OutReady-опитувалку (єдиний
   споживач Address Read) і поклавшись лише на WAIT-поля Data Write/Read, отримуємо відтворюваний
   `cmd 0x06 status=0x0D`. Це **перший робочий multi-step PI на Due** (раніше — лише шум/нулі).
2. **Читання даних FPDAT ЗАБЛОКОВАНО без Address Read.** Байти не просуваються: Block Read вертає
   16 однакових `0x03` і з (псевдо-)polls, і з fixed-delay `wr=100/rd=500µs`. Тобто це **не**
   timing-race — вказівник байтів FPDAT не інкрементується без per-byte OutReady-опитування, а воно
   робиться саме Address Read'ом. Get Version/Derivative однаково впираються в це (0x0D = статус, не
   значення).
3. **Lock-статус лишається НЕВІДОМИМ.** `0x03×16` — stale-latch артефакт, не flash (за адресою
   0x0000 — reset-вектор, не 16 однакових байтів). Будь-який автоматичний вердикт «not locked» на
   цих даних **недостовірний**.

**Що розблокує реальний дамп (усе впирається у робочий Address Read):**
- (b) **Uno** — x893 AVR-примітиви мають робочий Address Read (детермінований PORTD); треба лише
  резистор і на C2D (як на C2CK) через 5В-нетолерантний P2.0. **Найдешевший реальний форвард.**
- (a) **Due + зовнішній pull-up на C2D** (10к на 3.3V піна Due) + короткі дроти + твердий спільний
  GND — може стабілізувати turnaround настільки, що AR запрацює.
- (c) **EC2/EC3/ToolStick + ec2drv/ec2-new** — зріла реалізація коректного PI; найнадійніше.

> **Erase-safety, як зроблено:** Block Read у скетчі шле `count=0x10` (не `0x08`=Page Erase) і
> відправляє addr/count **лише** після `status==0x0D` на команду `0x06` — тож десинк не може
> перетворити аргумент на команду стирання. Жодна гілка не емітить `0x03`/`0x07`/`0x08`.

## 8. Застереження

- **Не робіть mass-erase** заради розблокування: він стирає й bootloader, який відновлює тільки
  виробник → пристрій стане непридатним для штатної прошивки.
- Перед будь-яким записом майте резервні образи `firmware/Uosc12{3,5,6}.ofw` (це і є єдина
  розповсюджувана форма прошивки).
- Плутати -RFS (C2CK) з C2Dat (C2D) — часта помилка: переплутаєте піни → зв'язку не буде,
  але апаратно це не шкідливо; переплутати живлення/землю — шкідливо.

## 9. ✅ РОЗВ'ЯЗКА: Raspberry Pi 4B + fast-C C2 → readback ЗАБЛОКОВАНО (2026-07-17)

Після того як Due (register-PIO/turnaround) і Uno (5В↔3.3В, C2D-read) уперлися, **перейшли на
Raspberry Pi 4B** — GPIO **нативно 3.3В**, як у чипа. Це зняло всі проблеми рівнів.

**Стенд і софт:**
- Розводка (пряме 3.3В, БЕЗ резисторів/шифтера): **C2CK=GPIO23** (фіз.16, =/RST), **C2D=GPIO24**
  (фіз.18, =C2Dat/P2.0), **GND** спільний. Перевірено на живому: hold GPIO23 low → scope мертвий
  (=/RST); GPIO24 падає в 0 коли scope у reset (=C2Dat, не power-rail).
- USB осцилографа лишається на ПК (cp210x; `sudo modprobe cp210x; echo 10c4 840e > /sys/bus/usb-serial/drivers/cp210x/new_id`) для OBEX-моніторингу (`scripts/test_connect.py`).
- Драйвер: **`firmware/rpi_c2/c2_rpi.c`** (+README; на RPi `~/c2_rpi.c`). Прямий `/dev/gpiomem` register bit-bang,
  `SCHED_FIFO`+`mlockall`. `gcc -O2 -o c2_rpi c2_rpi.c`; `sudo ./c2_rpi id` (читання Device ID,
  неруйнівне) / `sudo ./c2_rpi halt [addr] [len]` (halt+FPDAT Block Read — **морозить scope**,
  power-cycle після). SSH `yavfast@10.0.198.120`.

**Чому Python не годиться, а C — так:** C2 не має мінімальної частоти, але C2CK-low мусить бути
**<5µs** (інакше spurious /RST), і `reset→FPCTL-halt` треба встигнути, поки firmware не перехопив
P2.0. Python (lgpio/pigpio) занадто повільний і джитерний → firmware перехоплює C2D (читання=0xFF).
**Fast C** (~0.3–0.5µs strobe) виграє post-reset вікно.

**Результати (верифіковано):**
- **Device ID `0x0C` / Rev `0x02` — надійно** (fast C виграє вікно). **FPCTL-halt тримається**
  (fast strobes 300/500ns для race; back-to-back FPCTL; потім сповільнення для FPDAT). Halted
  DevID / AR-status `0x00` / GetVersion `0x0D` — усе чисто. **Address Read теж працює** (на відміну
  від Due).
- **🔒 Block Read → readback ЗАБЛОКОВАНО:** команда 0x06 приймається (`st1=0x0D`), addr/len
  пишуться, але **читання flash дає фіксовану помилку `st2=0x03` і РЕСЕТИТЬ пристрій** (scope
  оживає по OBEX). Контроль: halt **без** read — scope лишається halt-нутим (DEAD). Тільки
  **flash-read** ресетить; однаково на `0x0000` і `0x4000`, навіть 1 байт. Це класична сигнатура
  **flash-security**: читання захищеної сторінки → flash-error reset (див. debug-silicon).

**Висновок:** **простий C2-дамп flash НЕМОЖЛИВИЙ — readback залочено.** Отже **Path A**
(known-plaintext сторінка → keystream для `.ofw`) **ЗАКРИТО** без інвазивного обходу. Єдиний шлях
дістати flash — **voltage-glitch під Block Read** (ChipWhisperer; репо debug-silicon під F34x —
під F41x треба адаптувати FPDAT=0xB4 і піни). Для не-інвазивного напряму **ceiling ofw-mask
111/514 лишається межею**. C2 повністю працює для read-only команд/Device ID; firmware цілий.

**Безпечні read/debug-команди — перевірено на надійному RPi-лінку (`c2_rpi.c dbg`, 2026-07-17):**
- **Get Version (0x01) = `0x05`**, **Get Derivative (0x02) = `0x67`** (1-ше читання = статус `0x0D`,
  2-ге = значення). Тобто версія PI = 0x05, derivative-код = 0x67.
- **Direct Read (0x09) та Indirect Read (0x0B) — ВІДХИЛЕНІ** (status ≠ 0x0D) → **не реалізовані в
  PI цього F41x**. Це підтверджує ранній висновок з Due (тепер без сумніву про кривий лінк): PI
  F41x — **мінімальний flash-набір** (0x01/0x02/0x06/0x07/0x08 + erase), **без debug-команд**
  доступу до RAM/SFR. Отже C2-каналу «прочитати RAM/розшифровані буфери firmware» **немає**.

## 9a. Datasheet-обґрунтований доказ lock (C8051F41x datasheet §16.3/§26, 2026-07-17)

Датащит (авторитетний для F41x; AN127 — загальний) уточнив три речі:
1. **FPCTL enable = `0x02, 0x01`** (§26.4) — БЕЗ `0x04` (у AN127 було `0x02/0x04/0x01`). Драйвер поправлено; на результат Block Read це **не вплинуло** (сміття лишилось).
2. **FPDAT valid commands (§26.5): ЛИШЕ `0x06/0x07/0x08/0x03`** (Block Read/Write, Page/Device Erase). Немає `0x01/0x02` (Get Ver/Deriv) і `0x09–0x0C` (Direct/Indirect) → **офіційно підтверджує**, що debug/RAM-команди на F41x відсутні.
3. **§16.3 + Table 16.1:** flash має **Security Lock Byte** (останній байт user-space; лочить `n` 512-Б сторінок від page 0). Читання locked-сторінок через C2 = **«Not Permitted»**, і — ключове — **прохібовані C2-операції ІГНОРУЮТЬСЯ (do not cause device reset)**; FEDR-reset стосується **user-firmware**, не C2.

**⚠️ Уточнення мого раннього доказу (§9):** формула «read→reset ⇒ locked» **неточна** — reset виявився **недетермінованим** (`ARaf` іноді `0x00` = без reset) → артефакт таймінгу slow-FPDAT-фази, а **не** сигнатура lock. За датащитом справжня сигнатура locked-читання через C2 — **«ignored» (сміття, без reset)**.

**Емпіричний доказ — address sweep `0x0000→0x7DF0` (увесь flash), FPCTL=0x02/0x01:** кожен Block Read → `st1=0x0D` (команда прийнята), але **дані — address-INDEPENDENT сміття** (той самий обмежений алфавіт `FF/00/10/40/F2` на ВСІХ адресах; не 8051-код — нема LJMP `0x02`, нема багатого розподілу). Реальний flash був би **різним на кожній адресі**; **partial-lock лишив би високі сторінки читабельними** — жодна (0x0000, 0x2000, …, 0x7C00, Lock-Byte-регіон 0x7DF0) не дає реальних даних. Це і є документована поведінка **«locked flash → C2 read ignored»** на **всьому** чипі → **flash readback ЗАБЛОКОВАНО ПОВНІСТЮ**.

**Чесне застереження:** залізобетонний позитивний контроль (прочитати *відому* сторінку) на повністю-locked чипі неможливий, тож залишковий шанс латентного data-phase-quirk на 100% не виключений. Але: (а) командний рівень C2 повністю робочий, (б) датащит документує саме таку «ignored»-поведінку, (в) жодна сторінка з усього діапазону не читабельна. Вага доказів + механізм датащиту → **lock**. Практичний висновок незмінний: **не-інвазивний C2-дамп неможливий**; ceiling ofw-mask **111/514**; лише voltage-glitch під Block Read.
