## Context

Три прошивки `Uosc123/125/126.ofw` (кожна 30928 B) зашифровані **адитивним потоковим шифром з фіксованою
514-байтовою маскою (keystream), що повторюється щосектора** — це вже встановлено
(`firmware_update_method.spike.md` §9, tool `firmware/ofw_crypto.py`). Маска живе **тільки в bootloader
пристрою**, у ПЗ ПК її немає. Попередній висновок: «file-only відновлення вичерпане, потрібен C2-дамп».

Користувач попросив: **математичне обґрунтування** розв'язання; можливість зробити **тестову прошивку**
для визначення реальної структури відкритого тексту; fallback — **написати прошивку з нуля**. Цей spike
дає строгу модель, **новий регулярний шаблон** (stride-8), точну (перевалідовану) оцінку відновлюваної
частки маски і три шляхи до повної маски.

## 1. Формальна модель

Позначення. Payload розбито на `N` секторів по `L = 514` байтів; кожен сектор = одна 512-байтова
flash-сторінка C8051F34x + 2-байтове поле. Маємо 3 версії × 60 секторів = **N = 180** секторів під
**однією** маскою (усі `1.2Z` дешифрує один і той самий bootloader платформи 1.2 — підтверджено нижче).

Нехай `P[s][i]` — байт відкритого тексту, `C[s][i]` — шифротексту, `s∈{0..N-1}`, `i∈{0..L-1}`.
Шифр (адитивний потоковий, перевикористаний keystream `K` довжини `L`):

```
C[s][i] = (P[s][i] + K[i]) mod 256          (шифрування — у bootloader)
P[s][i] = (C[s][i] − K[i]) mod 256          (розшифрування)
```

**Ключові властивості (усі підтверджені експериментально на 3 файлах):**

| Властивість | Наслідок | Доказ (цей spike / §9) |
|---|---|---|
| **Адитивний, не XOR** | `K[i] = mode−background`, з переносами | перенос `0x0b→0x0c` у seq-полі (§9.1) |
| **Період рівно `L=514`** | стовпчикова атака: 180 зразків/байт маски | IoC 8.5% на лагах 514/1028/1542 (§9.1) |
| **Без зчеплення (no chaining), без дифузії** | зміна 1 байта P → зміна 1 байта C; **позиційний** шифр | `C[6]−C[8]=0` скрізь, крім offset 1 (§9.1) |
| **Маска спільна для версій** | 3 файли = 180 незалежних зразків на 1 байт маски | сектори 6/22/24 **body-ідентичні** 125↔126 (тіло cols 2..513); один bootloader платформи |
| **Не стиснуто** | розшифрування = проста віднімання, без reverse-decompress | `C125−C126=P125−P126` структуроване, 8.9% нулів |

> **Виправлення до §9 (важливо):** твердження §9.2 «сектори 6/22/24 **byte**-identical across versions»
> точне лише для **тіла** сектора (cols 2..513); повні 514-байтові сектори **не** збігаються (2-байтовий
> заголовок cols 0–1 різний → це per-sector поле цілісності+послідовності, а не частина сторінки).
>
> **2-байтове поле = CRC + SEQ (визначено byte-аналізом):**
> - **col0 = CRC / контрольна сума вмісту сторінки (8-біт).** Доведено *body-locked*: однакове тіло
>   сторінки ⇒ однаковий col0 по **всіх 180 секторах усіх 3 версій** (дублі-сторінки в межах версії
>   мають однаковий col0 — перевірено на групах {6,8,12,14,19,28}=0xD3, {10,22}=0x97, {20,24,27}=0xF5).
>   Це **1 байт** (не 16-біт: col1 — це SEQ, а не молодший байт CRC). Конкретний алгоритм (CRC-8 / сума /
>   xor-fold) **не визначити без plaintext** (не можна порахувати контрольну суму над невідомим вмістом).
> - **col1 = SEQ — РОЗШИФРОВАНО (K[1]=0x06 відновлено, §3a).** `SEQ_plain = (0x20·L) mod 255`, де
>   `L` = логічний номер flash-сторінки (0..58); кінцевий сектор має `L=254 (≡ −1)` — sentinel «E».
>   `K[1]=0x06` — **єдине** значення, що дає чистий набір `{0..58}+{sentinel}` в усіх 3 версіях.
> - `K[0]` (CRC) лишається зашифрованим (у реконструкції — сирий шифротекст `CRC_істин=(CRC−K[0])&0xFF`).

### Що таке «маска розпакування»
Це саме вектор `K = (K[0], …, K[513]) ∈ (ℤ/256)^514`. **Розпакувати будь-яку `.ofw` = знати `K`.**
Одна відома сторінка відкритого тексту дає всю маску (див. §5). Задача розпакування **зводиться** до
відновлення `K`.

## 2. Задача відновлення = «many-time pad» (перевикористаний одноразовий блокнот) за mod 256

Оскільки `K` перевикористовується для всіх `N` секторів, для кожного стовпця `i` маємо `N` рівнянь:

```
C[0][i] = P[0][i] + K[i]
C[1][i] = P[1][i] + K[i]
   ⋮
C[N-1][i] = P[N-1][i] + K[i]          (усі mod 256)
```

Це класичний **many-time pad**: маска скорочується в різницях `C[s][i] − C[t][i] = P[s][i] − P[t][i]`
(відомо!), але сам `K[i]` визначається лише з **надлишковості відкритого тексту** в стовпці.

**Теорема відновлюваності (стовпцева).** `K[i]` відновлюється ciphertext-only **тоді і тільки тоді**,
коли розподіл відкритого тексту `D_i = {P[s][i]}_s` має **відомий якір** — значення `b*` з відомою
семантикою, що є строгою модою:

```
∃ b* :  Pr[P[·][i]=b*] > max_{v≠b*} Pr[P[·][i]=v]
  ⇒  argmax_v freq_s( C[s][i]=v )  =  (b* + K[i]) mod 256
  ⇒  K[i] = (mode_i − b*) mod 256.
```

Надійність оцінки ∝ **розрив** `p_i − p_i^{(2)}` (мода мінус друге значення) та глибина `N`.
Якщо ж `D_i` рівномірний (щільний код/дані без якоря), стовпець є **справжнім one-time pad**:
`K[i]` **інформаційно-теоретично не визначається** жодною кількістю самих лише шифротекстів.

**Наслідок (нижня межа неможливості):** частка маски, яку можна дістати з файлів, обмежена часткою
стовпців, де відкритий текст має відомий якір. Решта потребує **відомого відкритого тексту** (§5).

## 3. Регулярний шаблон, знайдений у byte-code: **stride-8, offset≡4 (mod 8), якір = 0xFF**

Це головна нова знахідка цього spike (попередній аналіз трактував сторінку як монолітний
високоентропійний блок і **пропустив** її).

### 3.1 Спостереження
- **Стовпцева ентропія** (по 180 зразках) низька: середня **5.37 біт**, max 6.19 — тобто стовпці
  структуровані (хоча сукупна ентропія payload 7.98 — бо мода кожного стовпця зсунута на свій `K[i]`).
- **Background-доміновані стовпці** (мода-частка ≥ 0.20) розташовані **рівно через 8 байтів**:
  гістограма розривів між сильними стовпцями = `{8: 60}`. Стовпці `{6,14,22,30,38,…,510}` —
  усі на **offset ≡ 4 (mod 8)** у тілі сторінки (512/8 = **64** слоти по 8 байтів).
- У ~36 секторах (з 180) ці стовпці **одночасно** сидять на моді (бімодальний розподіл: 33 сектори
  збігаються по **всіх** stride-стовпцях, ~60 — по жодному).
- **Якір = 0xFF (стерта flash).** Розшифрування stride-стовпців сектора з `K = mode − 0xFF` дає
  **рівно 0xFF** на всіх 64 позиціях. Тобто:

```
K[i] = (mode_i − 0xFF) mod 256 = (mode_i + 1) mod 256     для i ∈ {6,14,22,30,…,510}
```

### 3.2 Інтерпретація
Прошивка містить багато **майже стертих сторінок** (до **86.8% 0xFF**; дві сторінки збігаються в
**513/514** байтах — та сама сторінка на різних позиціях). Дані в них займають offsets `{0,1,2,3,5,6,7}`
кожного 8-байтового слоту, а **offset 4 лишається 0xFF** — це і є регулярна «маска-крізь-дані», що
відкриває 64 байти keystream. (Ймовірне походження — 8-байтове вирівнювання структур/таблиць firmware;
точну семантику підтвердить тестова прошивка, §6.)

### 3.3 Потрійна перехресна валідація 64-байтової маски
Ці 64 байти `K` — **надійні** (не артефакт), бо збігаються за трьома **незалежними** методами:

| Метод | Результат |
|---|---|
| Мода по всіх 180 секторах, якір 0xFF | 64 стовпці, розрив мода−друге ≥ 0.10 (61/61 у діапазоні 30..510) |
| Консенсус лише «стертих» сторінок | ті самі 64 стовпці при порозі ≥0.7 |
| **Version-split**: `K` з {123} vs `K` з {125,126}, незалежно | **0 розбіжностей** на цих 64 стовпцях |

**Відновлено ciphertext-only: 64 / 514 байтів маски = 12.5%** (+1 байт `K[1]` нижче → **65/514**).

## 3a. SEQ-поле (col1) розшифровано → `K[1]` відновлено + справжня карта адрес

Друга (окрім stride-8) точка входу — **known-plaintext через структуру SEQ**.

### 3a.1 Модель і відновлення `K[1]`
Col1 кожного сектора кодує **логічний номер flash-сторінки** `L` за формулою:
```
SEQ_plain(L) = (0x20 · L) mod 255 ,   C[s][1] = (SEQ_plain + K[1]) mod 256
зворотно:  L = ( 8 · ((C[s][1] − K[1]) mod 256) ) mod 255          (8 = 32⁻¹ mod 255)
```
- **`K[1] = 0x06`** — це **єдине** значення (перебір усіх 256), за якого декодовані `L` в **кожній** з
  3 версій утворюють чистий набір `{0,1,…,58}` + один **sentinel `L=254 (≡ −1)`** (кінцевий сектор «E»).
  Діапазон підтверджує: `L=0→C=0x06` (min), `L=55→C=0xEC` (max) — точно як спостережено.
- Це **known-plaintext стовпець**: `SEQ_plain` — детермінована функція позиції, тож `K[1]` точний.
  **Маска: 64 → 65/514.** (Чому лише +1, а не більше: SEQ — єдиний стовпець із *відомою* невипадковою
  структурою поза 0xFF-решіткою; CRC(col0) залежить від невідомого вмісту, решта — щільні дані.)

### 3a.2 Наслідок: сектори у файлі ПЕРЕСТАВЛені; SEQ дає справжню адресу
`.ofw` зберігає 60 секторів у **переставленому** порядку — і перестановка **різна в кожній версії**
(відрізняється в 59–60/60 позицій). SEQ→`L` відновлює справжнє розташування:
`addr(L) = 0x0400 + L · 0x200`. Це **виправляє** здогад «file-order = адреса» (стовпець `ADDR~` у
реконструкції → тепер справжній `ADDR` з `L`). Хвіст файлу зазвичай уже в логічному порядку
(Δseq=0x20), голова — переставлена.

### 3a.3 Справжня карта сегментів (за логічною адресою, 1.26)
```
L:   0         1         2         3         4         5
     0123456789012345678901234567890123456789012345678
cls: ..............EEEEEEEEEEE....mE..m.........................   (E=0xFF@lattice, m=mixed, .=data)
```
За логічним порядком структура **чистіша**, ніж за file-order: суцільний блок `ff@lattice`
**L=14…24** (`0x2000–0x36FF`) — цілісний сегмент (велика таблиця/резерв), який у file-order був
розсіяний. **18/59** логічних сторінок **байт-ідентичні в усіх 3 версіях** (стабільні дані/таблиці);
решта — код, що перекомпілюється.

## 3b. Метод «судоку»: ознаки для підбору й перевірки `K[i]`

Кожен `K[i]` має 256 кандидатів; «правила» — сигнатури валідної 8051-прошивки. Шифр позиційний
(стовпці незалежні), тож зв'язок **між** стовпцями дають лише багатобайтові структури plaintext
(опкоди, адреси, рядки) — це й робить задачу складною (у щільному коді структура слабка).

### Anchor-сигнатури (дають / звужують `K[i]`)
| # | Ознака | Дає | Статус |
|---|--------|-----|--------|
| A1 | Стерта flash `0xFF` на решітці offset-4-mod-8 (ff@lat) | 64 байти (`K=C+1`) | ✓ |
| A2 | `SEQ = (0x20·L) mod 255` | `K[1]=0x06` | ✓ |
| A3 | Reset LJMP: `P[0x0400]=0x02` (крос-версійно) | `K[2]=0x33` | ✓ |
| A4 | Вектор-слоти `0x0403+8n`=LJMP(0x02); target-hi (латтіс, K відомий) ∈ [0x04,0x7B] | **12 байтів** cols 5,29,37,53,61,69,77,85,93,101,109,117 | ✓ high-conf |
| A5 | LJMP/LCALL операнд = адреса ∈ [0x0400,0x7BFF] → hi ∈ [04,7B] | звужує сусідні cols | частково |
| A6 | RET/RETI (0x22/0x32) у кінці підпрограм | кандидати | — |
| A7 | 8051-опкод-граматика (0xA5 заборонений; рідкісні опкоди) | слабко звужує | — |

### Verify-сигнатури (перевірка кандидата / повного decrypt)
V1 ентропія сторінки 7.98 → ~5–6 · V2 з'являються криби (`Oscill.com`,`Uosc`,`VSW`,`VNM`,реєстри) ·
V3 CRC(col0) узгоджений (алгоритм ще невідомий) · V4 крос-версійна когерентність (identical-C→identical-P) ·
V5 друковані ASCII-рядки · V6 LJMP-цілі влучають у код-сторінки, не дані/erased.

### Region-криби
Таблиця векторів L=0 (перші ~0x80 B, 8-байтові LJMP-слоти) · C-startup одразу після (стереотипний
Keil `?C_STARTUP`, зіставний з референсом) · стабільні дані-сторінки (18/59) = таблиці/LUT.

### Результат методу (без заліза)
Ланцюг A1→A4 підняв маску **65 → 78/514 (15.2%)** і відновив **карту векторів вендора**:
INT0→0x1bxx · Timer1→0x26 · UART0→0x27 · SPI0→0x07 · SMB0→0x34 · USB0→0x66 · ADC0-WC→0x48 ·
ADC0-EOC→0x66 · PCA0→0x37 · CMP0→0x6d · CMP1→0x0d (невикористані: Timer0/Timer2 hi=FF; INT1 — аномалія hi=0xf7; уточнено в §3c).
`firmware/ks_partial.json` містить 78 байтів з полем `confidence`. **Валідація:** таблиця векторів L=0
читається як коректна 8051 — **16/16** слотів (12 LJMP з target-hi у діапазоні + 4 unused). **Межа
досягнута (~78):** vector-anchor спрацював завдяки збігу — target-hi байти лягли рівно на решіткові
стовпці (offset-4-mod-8, K відомий); цей збіг вичерпано. Startup-регіон L=0 — версійно-змінний код
(лише 19/64 решіткових стовпців стабільні), без нових lattice-вирівняних якорів. У щільному коді без
якорів V-сигнатури надто слабкі при глибині 180 → пропагація згасає (§4). Це межа **vector-anchor**-методу;
crib-drag (§3d) далі підняв маску до **106/514** без known-page. Повна (514) маска потребує known-page.

## 3c. Спроба «судоку» на сторінці векторів (LJMP+FF): розширення 78→148 **ВІДХИЛЕНО** (2026-07-15)

Гіпотеза (уточнена користувачем): перша сторінка `L=0` — таблиця з 16 8-байтових слотів, кожен
`LJMP(02 hi lo)+5×FF` (used) або суцільний `FF`/`RETI` (unused). Попередній збір узяв лише **opcode**
(≡3 mod8) та **target-hi** (решітка ≡4). Незібраними лишались **gap-байти** (заповнювачі ≡6,7,0,1,2 mod8)
і слоти невикористаних векторів. Ідея: якщо gaps = `0xFF`, то `K=C−0xFF` дає ~70 нових стовпців → 148/514.

**Метод — валідний.** Крос-версійна рівність: K спільна ⇒ `C_a−C_b=P_a−P_b`, отже стовпець із **константним
P у всіх версіях ⟺ рівний C** (тест без знання K). Anchor-перевірка **ПРОЙДЕНА**: усі 12 відомих opcode-
стовпців декодуються у `0x02` і крос-версійно рівні.

**Структуру підтверджено** (декодом решітки+opcode): 16 слотів — **12 used** (INT0, Timer1, UART0, SPI0,
SMB0, USB0, ADC0-WC, ADC0-EOC, PCA0, CMP0, CMP1, vec15; hi∈[07,7b]); **2 unused-FF** (Timer0, Timer2; hi=`0xFF`);
**1 аномальний INT1** (hi=`0xf7` — не FF і не діапазон коду; імовірно `LJMP` у high-flash `0xf7xx`
bootloader-trap, з файлів **не підтверджувано** → не додано).

**FALSIFIED — gap-байти НЕ є стертим `0xFF` (доказ):**
| Доказ | Деталь |
|---|---|
| **Крос-версійна різниця C** | `off7`(gap INT0)=`07/07/06`, `off88`(ADC0-EOC), `off95/98`(PCA0) різні по версіях. Спільна K ⇒ однаковий `0xFF` дав би однаковий C; різний C ⟹ **P≠0xFF**. **3/12 used-слотів** мають доведено НЕ-FF gap. |
| **Еталон SDCC** | unused-слот = `32(RETI)+FF`, тобто навіть «unused» ≠ суцільний FF. |
| **Many-time-pad (§2)** | решта gap-байтів крос-версійно **константні**, але «константа» ≠ «`0xFF`»: після доведення, що gaps несуть контент, значення константного gap-байта інформаційно приховане й **з файлів невизначуване**. |

**Наслідок:** 70 «кандидатів» = непідтверджена **FF-гіпотеза**, спростована для частини слотів → їх коміт
**зіпсував би** маску (`K=C−0xFF` там, де `P≠0xFF`). Vector-table «судоку» через FF-padding **вичерпана**.
Скрипти: `scratchpad/sudoku_*.py` (throwaway). Позитив: повна карта used/unused слотів і target-hi
перевалідована (16/16 когерентні). Низькоімовірні кандидати → `firmware/ks_conjectural.json`.

## 3d. Crib-dragging відомих ASCII → +28 байтів (hex-LUT), **78 → 106/514** (2026-07-15)

Після невдачі з vector-table застосовано **crib-dragging**, валідований 64 lattice-байтами: якщо відомий
рядок `P*` стоїть у (сектор s, стовпець c0), то `K[c0+j]=C[s][c0+j]−P*[j]`; там, де `c0+j` потрапляє на
**відомий** стовпець (lattice), похідний `K` **мусить** збігтися з відомим. 16-байтовий crib перетинає
**≥2 lattice-стовпці** → ≥16-біт фільтр на ~90k позицій ⇒ хибних майже нема; додатковий фільтр —
**крос-версійна когерентність** (той самий рядок на тому самому c0 у кількох версіях).

**Знахідки (обидві перевалідовані):**
| Crib | Сторінка / col | Версії | Нових суміжних `K` |
|---|---|---|---|
| `0123456789ABCDEF` (hex-LUT великих) | L=11, col439 | **усі 3** (тіла сторінок різні, але 16-байтовий шифротекст ідентичний) | 14 |
| `0123456789abcdef` (hex-LUT малих) | L=10, col207 | 123, 125 (у 126 сторінку змінено/прибрано) | 14 |

**Разом +28 суміжних байтів → 106/514 (20.6%)**, конфліктів із 78 — нема; декод сторінок читає LUT-и
чисто. Пристрій **використовує hex-транспорт** (skill `signal_processing/hex_encoding_protocol`) → hex-LUT
гарантовано присутні; ось чому саме вони «спрацювали».

**Що НЕ знайдено** (crib-drag, ≥2 lattice, вичерпно): банер `Oscill.com oscilloscope firmware.` (**немає**
у payload verbatim), одиниці (`mV/kHz/s/div/V/div`), алфавіти (`ABC…`, `abc…`), UTF-16 рядки дескрипторів,
**sine/ramp 256-LUT** (best lattice-agreement 4/32 = випадковість), USB device descriptor (1 версія, слабко →
відкинуто). Тобто довгих числових таблиць у payload немає; єдині довгі криби — два hex-LUT.

**Коригує §9 / skill «криби ≤4 байти, надто короткі»:** для **register-імен** (VSW…) — так; але **16-байтові
hex-LUT** достатньо довгі (перетин 2 lattice) і гарантовані hex-транспортом → crib-drag тут **працює**.
`ks_partial.json` тепер має тир `confidence`: `proven`(66) / `vector-hi-conf`(12) / **`crib-validated`(28)**.
Скрипти: `scratchpad/crib_drag.py`, `crib_validate.py`, `mine_luts.py` (throwaway).

## 3e. Neighbor-extension довкола двох довгих сегментів — СПРОБУВАНО, БАР'ЄР (2026-07-15)

Запит користувача: пройтися по **відновлених довгих сегментах** і відновити **сусідні** байти за
контекстом — «якщо це частина коду функції» або за іншим статистичним/шаблонним патерном. Довгі
сегменти рівно два (єдині contiguous-run ≥3): **A** = cols 206–222 (lowercase hex-LUT @ L=10),
**B** = cols 438–454 (uppercase hex-LUT @ L=11). Обидва — 17-байтові рядки (LUT + обрамлювальні
lattice-байти). Результат: **жодного нового байта; бар'єр §2 стоїть точно на межі сегментів.**

### 3e.1 Ключова структурна знахідка: дзеркальна крос-версійна поведінка двох LUT-сторінок
| Сегмент | Сторінка | Крос-версійно | Сусіди (обидва боки) |
|---|---|---|---|
| **A** lowercase | L=10 | v123==v125, **v126 відрізняється цілком** (507/512 cols варіюють) | **усі VARY** |
| **B** uppercase | L=11 | **байт-ідентична в усіх 3 версіях** (лише 6/512 cols варіюють: 6,66,67,126,129,132) | **усі CONST** |

Це рівно два **різні** підвипадки теореми §2 — і **обидва невідновлювані з файлів**:
- **A (сусіди VARY):** відкритий текст сусідів **версійно-специфічний** → це справжній **one-time pad**
  (кожна версія дає інший невідомий байт, немає якоря) → інформаційно невідновлюваний.
- **B (сусіди CONST):** відкритий текст сусідів **константний у всіх версіях**, але **без якоря** —
  three identical copies несуть **нуль** інформації про *значення* (many-time pad з усіма різницями = 0).
  Відновлюваний лише з зовнішнім plaintext (known-page / 4-та розбіжна версія), не з цих 3 файлів.

### 3e.2 Чому «код функції» не допомагає (навіть якщо L=11 — це код)
Відомі байти на не-LUT-сторінках — **лише lattice (1 байт на 8)**. 8051-дизасемблювання вимагає меж
інструкцій, а щоб знати, де починається інструкція `i`, треба довжину `i−1` (її опкод), який невідомий,
якщо не lattice. З 1 відомим байтом на 8 межі інструкцій **не встановлюються**. Плюс усі байти 0x00–0xFF,
окрім `0xA5`, — валідні опкоди → граматика **не звужує** кандидатів. Отже code-context дає **0** важелів
за наявної розрідженості (підтверджує §3b: «пропагація згасає у щільному коді»).

### 3e.3 Вичерпний перебір довгих крибів (з повним 106-байтовим валідатором) — 0 реальних збігів
Перевалідовано (≥2 lattice-overlap + крос-версійна когерентність), `scratchpad/crib_extend.py`,
`reg_crib.py`: **base64**-алфавіт, **ASCII-printable** (0x20–0x7e), **лінійний ramp** 0..255 / 0..63 /
step-2, **великий/малий алфавіт**, **register-name таблиця** (VSW/VSN/…/AVG у concat / null-sep /
`{name,type,addr}`-record розкладках), **MOVC-рутина** `MOV DPTR,#0x18CD|0x1BB5 / MOVC A,@A+DPTR`
(routine, що *використовує* LUT), і **продовження LUT** (`+lower`, `+NUL`, `+space`). Усе — **0**
збігів ≥2-lattice. Єдині 2-lattice «хіти» (`digits20`, `names_nul`) — **доведені false-positive**:
сидять на logical page L=7, де run **варіює** крос-версійно (константний рядок там неможливий). Тест
`upper+NUL` і `hex+space` дають **ідентичні** хіти (обидва лише перезнаходять 16 байтів LUT) → 17-й
байт (c455) **не валідується** → продовження LUT з файлів невизначуване.

### 3e.4 Побічний корисний артефакт: крос-версійна карта константності (для майбутньої C2-атаки)
Сегмент B лежить у **381-байтовому** суцільному крос-версійно-константному блоці (cols 133–513 на L=11:
76 уже-відомих, **305 константних-але-без-якоря**); ще два блоки cols 7–65 (48 unknown-const) і
68–125 (44 unknown-const). L=11 — одна з **18 стабільних** логічних сторінок → hex/OBEX-транспорт живе
в **стабільному** регіоні (добре для template-match, якби зʼявився справжній компілятор/asm-джерело;
поки — ні, §5.5). **Наслідок для C2:** одна known-page будь-якого індексу дає всю маску (`K=C−P`);
карта константності лише каже, *які* сторінки версійно-стабільні (найбезпечніші для реконструкції/валідації).

**Висновок §3e:** neighbor-extension **не** розширює маску — сегменти стоять точно на межі §2
(A = OTP, B = unanchored-const). Відповідальних «ймовірних кандидатів» для цих сусідів з файлів
**не існує**; статистичний здогад (напр. «0x00 як найчастіший опкод») інжектнув би **хибний** `K` —
це пастка §4. **Neighbor-extension нічого не дало** (маска лишилась 106/514 на цьому кроці; згодом §3f
підняв її до 107 іншим методом — LJMP-решіткою, не сусідами); `ks_partial.json` цим кроком **не змінено**,
у `ks_conjectural.json` **нічого не додано** (немає кандидатних *значень*). Скрипти: `scratchpad/neighbor_scan.py`,
`page_dump.py`, `crib_extend.py`, `reg_crib.py` (throwaway).

## 3f. Сторінка L=0: повна LJMP-решітка таблиці векторів → +1 доведений, +4 кандидати (2026-07-15)

**Контекст (уточнення користувача):** C2-**читання ЗАБЛОКОВАНО** (security-lock; readback вимкнено) →
Спосіб А (просто «дампнути сторінку») **відпадає** без glitch-bypass. Отже треба вичавити максимум з
**file-only** структури. Користувач указав на **регулярну структуру `0x02`** у таблиці векторів L=0 і на
можливе **`0xFF`/NOP-заповнення після кінця функції**. Обидві гіпотези перевірено на L=0 (усі 3 версії),
`scratchpad/l0_vectors.py`, `l0_full.py`.

### 3f.1 Геометрія (app @0x0400)
Reset `LJMP` @0x0400 (cols 2,3,4); IRQ-вектор `n` @`0x0403+8n`: **opcode col = 5+8n**, **target-hi col =
6+8n** (це **lattice** ≡6 mod8, K відомий!), target-lo col = 7+8n. C8051F340 = **16 IRQ-векторів**
(slots 0..15, cols 5..125) + reset. Тобто **target-hi кожного вектора лежить на решітці** — тому §3b і
дістав вектор-hi «безплатно».

### 3f.2 Таблиця векторів — **повна LJMP-решітка** (усі slot-opcode крос-версійно константні)
| Клас | Slots | Опкод P=0x02 | Дія |
|---|---|---|---|
| **USED-LJMP** (hi ∈ app-range 0x04–0x7f) | INT0,Tmr1,UART0,SPI0,SMB0,v8–v14 (12) **+ col133** | **доведено** | 12 вже були; **col133 — НОВИЙ** |
| **written-trap** (hi = специфічний non-FF) | INT1 (hi=0xf7), v15 (hi=0xf1) | high-conf | кандидати |
| **hi=0xFF (ambiguous)** | Tmr0, Tmr2 | ? | кандидати (LJMP 0xFFxx vs erased) |

- **col133 = `02 0d xx` (LJMP 0x0Dxx)** — перша інструкція коду **одразу після** 16-векторної таблиці
  (0x0400+3+16·8 = 0x0483 = col133). hi=0x0d в app-діапазоні → **однозначний LJMP** → `P=0x02` →
  **`K[133]=0x29` ДОВЕДЕНО** (той самий клас доказу, що й 12 vector-hi-conf). **Маску промотнуто 106→107.**
- **INT1 (col21, hi=0xf7) і v15 (col125, hi=0xf1):** hi — **специфічне записане** значення (≠FF) на
  позиції решітки-вектора ⇒ слот **записаний** (не стертий) ⇒ це `LJMP 0xf7xx`/`0xf1xx` (пастка в
  bootloader) ⇒ opcode `0x02` ⇒ `K[21]=0xc1`, `K[125]=0xdf`. Впевненість **structural-high** (єдине
  недоказне — сама high-flash ціль). У `ks_conjectural.json`, топ-кандидати на промоцію.
- **Tmr0 (col13) / Tmr2 (col45): hi=0xFF — принципово неоднозначні.** `02 FF xx` (LJMP 0xFFxx, як
  роблять INT1/v15) → `K=0xab/0x06`, **АБО** стертий слот `FF*8` → `K=0xae/0x09`. З файлів `hi=FF` **не
  відрізнити** LJMP-до-верху-флеша від erased → лишаються кандидатами (3 варіанти) у `ks_conjectural.json`.

### 3f.3 «FF/NOP після кінця функції» — у таблиці векторів **не підтверджено**
Gap-байти used-слотів (offsets 3–7 після `02 hi lo`) крос-версійно **константні, але НЕ `0xFF`/`0x00`** —
це **упакований код/дані** (напр. INT0 gaps = `c6 07 7f 93 0e`), а не padding. Тобто вектори **не**
`LJMP+padding`, а щільно набиті (короткі ISR inline / код у проміжках). Значення gap-байтів з файлів
невизначувані (constant≠known-value, §2). Підтверджує §3c: FF-harvest gap-байтів **хибний**.

### 3f.4 Підсумок §3f
**Маска 106 → 107/514** (доведений `K[133]=0x29`). **+4 structural-кандидати** у `ks_conjectural.json`
(INT1/v15 = high-conf `0x02`; Tmr0/Tmr2 = ambiguous). Якщо ззовні підтвердити, що **всі** unused-вектори —
`LJMP` (а не erased), маска стане **111/514**. `0x02`-регулярність користувача **підтверджена**
(таблиця — повна LJMP-решітка); «FF-padding» — **ні** (проміжки = код). Скрипти:
`scratchpad/l0_vectors.py`, `l0_full.py`, `update_conjectural.py` (throwaway).

## 3g. Каталог байт-патернів скомпільованого коду (prologue/epilogue-якорі) — 2026-07-16

**Ідея (користувач):** використати регулярності зібраного 8051-коду, щоб з великою ймовірністю
визначати однобайтові плейнтекст-байти `P[i]` у відомих позиціях → `K[i]=(C[i]−P[i]) mod 256`.
Приклади: перед початком функції — `RET`/`RETI` попередньої; на початку функції — робота зі стеком.
**Емпірично звірено з референс-збіркою `firmware/reference/ref0400.rst`** (SDCC 4.5.0, той самий
`__interrupt`-набір {0,1,4,5,8,10,11}, `--model-small`, target 0x0400) — не з пам'яті.

### 3g.1 Каталог (значення, ймовірність, що потрібно знати, щоб застосувати)

| # | Патерн (позиція → `P`) | Опкод | Надійність на SDCC | Що потрібно знати | Тип сигналу |
|---|------------------------|-------|--------------------|-------------------|-------------|
| E1 | байт **перед** fn-start звичайної C-функції = `RET` | `0x22` | висока, **але не єдина** (див. E-caveat) | стовпець fn-start | narrow-variant |
| E2 | байт **перед** fn-start = `RETI` (якщо попередник — ISR) | `0x32` | висока для ISR | стовпець fn-start | narrow-variant |
| P1 | 1-й байт **нетривіального** ISR = `PUSH ACC` | `0xC0` | **~60% (умовна!)** | стовпець ISR-entry (=vector target) | prior, НЕ якір |
| P2 | 1-й байт звичайної C-функції = `MOV R7,DPL` (передача 1-го арг.) | `0xAF` | середня (залежить від сигнатури) | стовпець fn-start | prior, НЕ якір |
| S1 | `__sdcc_program_startup` = `LJMP _main` | `0x02` | висока (структурно) | стовпець program_startup | anchor (opcode) |
| S2 | crt0 gsinit: `MOV SP,#stacktop` / `CLR A`+`MOVX @DPTR,A`-цикл | `0x75/0xE4/0xF0` | середня | стовпець gsinit | prior |
| R1 | reset/vector-slot = `LJMP addr16` | `0x02` | **доведено (§3f)** | grid-позиція (відома) | **вже зібрано** |

### 3g.2 Головна корекція гіпотези користувача (емпірична)

**«Функція починається зі стекових операцій» — для SDCC 8051 НЕ виконується** (на відміну від
Keil-reentrant / інших ABI):
- SDCC/`--model-small` розміщує локальні змінні **статичним overlay**, а НЕ у стековому кадрі →
  **звичайні функції не роблять PUSH узагалі**. Референс: `_adc_to_mv`, `_detect_segments`,
  `_hex_encode` усі починаються з `AF 82` (`MOV R7,DPL` — забір 1-го аргументу), `_main` — з
  `12 07 37` (`LCALL _hw_init`). Жодного `C0`.
- **ISR** пушать **лише** реально зачеплені `ACC/DPTR/PSW/регістри**, і оптимізатор SDCC
  **викидає зайві push/pop** для тривіальних leaf-ISR. Референс: `_ext0_isr`/`_timer0_isr`/`_adc0_isr`
  починаються з `C0 E0` (push acc), але `_uart0_isr` — з `10 98 02` (`JBC`), `_pca0_isr` — з
  `C2 DF` (`CLR bit`). Тобто 1-й байт=`0xC0` тримається лише в **3 з 5** ISR-ів → це **статистичний
  пріор ~60%, а не детермінований якір**. Використати його як hard-known plaintext = впасти в
  **пастку §4** (зіпсувати валідатор). Тому P1/P2 позначені «prior, НЕ якір».

**«RET/RETI перед fn-start» — валідне звуження, але не єдиний байт** (E-caveat):
- Підтверджено: ISR завершуються `32` (RETI), звичайні функції — `22` (RET) (референс). Це і є
  чинний сигнал `S-epilogue` у солвері (`TERMINATOR_OPCODES={0x22,0x32}`).
- Але (а) попередня функція може закінчуватися **багатобайтовим** переходом (`LJMP/SJMP/AJMP/ACALL`,
  tail-call/спільний епілог) → останній байт = **операнд** (будь-яке значення), не якір; (б) навіть
  коли термінатор однобайтовий, вибір `RET` **проти** `RETI` — це вгадування → сигнал дає {`0x22`,`0x32`}
  (+pad), **ніколи не unique** (C_OMS_DEC_02).

### 3g.3 Вердикт застосовності (проти поточного файлового знання) — **0 нових байтів**

Усі патерни каталогу вимагають **відомого стовпця початку функції**. Наразі відомий лише **один**
повний fn-start — `0x0483` (`RESOLVED` reset-target), і він сам є **трампліном** `LJMP 0x0Dxx`
(не має prologue-стеку; opcode `0x02` вже зібрано як `K[133]`). Тіла ISR-ів **не змаплені за
стовпцями** (vector target-**lo** невідомі, не на решітці — див. §3f/§4). Тому:
- **E1/E2 (epilogue):** спрацьовує лише на `col 132` (перед `0x0483`) → дає `{0x22,0x32,pad}` варіанти,
  ніколи unique. **⚠️ Модельна неточність:** `0x0483 = 0x0400+0x83`, а слот v15 (`__interrupt 15`)
  займає `0x047B..0x0482`, тож `col 132 = 0x0482` — це **хвіст таблиці векторів** (проміжок слота),
  а **не епілог функції**. Отже цей кандидат — той самий packed-gap із §3f/§3c, а не чистий термінатор
  → **не підвищувати впевненість**. Реальних міжфункційних меж поза grid-таблицею наразі **нема**.
- **P1/P2 (prologue):** цілі ISR/функцій не змаплені → **ніде поставити**; до того ж це пріори, не якорі.
- **S1/S2 (crt0):** `program_startup`/`gsinit` — за адресою `0x0Dxx` (target-lo невідомий) → **ніде поставити**.

**Підсумок §3g:** каталог **не зрушує 111/514 з файлів** — упирається в ту саму стіну відсутнього
**вирівнювання/змапленого fn-start** (§4). Його цінність — це **заряджений сигнал під зовнішній
важіль**: щойно з'явиться ≥1 змаплений початок функції (більше версій, які дадуть target-lo, або
C2/glitch known-page), epilogue-якір (E1/E2) і opcode-якорі (S1,R1) спрацьовують негайно; пріори
(P1/P2/S2) лишаються **лише перевіркою**, не джерелом байтів. Пастка §4 (частотні опкоди `0x00`,
`MOV A,Rn`… як «known plaintext») **лишається забороненою** — каталог її не легалізує.

### 3g.4 Реалізація в солвері: S-prologue як **двобайтові** пріори з крос-перевіркою (2026-07-16)

Пріори P1/P2 реалізовано в `ofw_mask_solver.py` (`prologue_candidates`, команда `jumps`) як
**2-байтові** патерни входу (`P[entry],P[entry+1]`), тобто кожен кандидат передбачає **два** байти
keystream. Набір (звірено з `ref0400.rst`), градуйований довірою:

| tier | патерн | сенс | база |
|------|--------|------|------|
| primary | `AF 82` | `MOV R7,DPL` — звич. фн, скалярний 1-й арг | **4/4** ref-функцій зі скалярним 1-м арг |
| primary | `C0 E0` | `PUSH ACC` — нетривіальний ISR | 3/7 ISR |
| secondary | `AE 83` | `MOV R6,DPH` — 2-байтовий (int/ptr) 1-й арг, старша половина | конвенція SDCC (нема в ref) |
| variant | `AE 82`/`AD 82` | `MOV R6/R5,DPL` — альтернативна алокація регістра | — |

**Крос-перевірка (справжній фільтр):** якщо `entry+1` потрапляє на **відомий** стовпець (напр.
0xFF-решітку), похідний `K[entry+1]` порівнюється зі знаним → кандидат `validated`/`refuted`.
`refuted` = **виключено**; `validated` = **узгоджено, але не доказ** (функція може мати інший пролог).
Демо: на фіктивному «fn-start» = col13 (насправді слот вектора Tmr0) відома решітка `K[14]=0xea`
**спростовує ВСІ 5 патернів** — це і є дискримінаційна сила фільтра. **Ніколи не пишеться в
`ks_partial`** (soft prior, не hard-anchor). Сьогодні стріляє на **0 цілей** (єдиний змаплений fn-start
0x0483 — трамплін із уже відомим стовпцем входу). Тест: `scripts/test_ofw_solver_window.py`.

### 3g.5 Повний пошук по патернах — **ВИМІРЯНО: нижче шумового порога, 0 байтів** (2026-07-16)

Запущено пошук по всіх 10 кодових сторінках × усіх 111 відомих стовпцях (`scratchpad/prologue_search.py`),
у двох напрямках. Валідатор має «зуби» лише там, де сусідній байт кандидата — **відомий** стовпець:

| Напрям пошуку | Очікування (випадок) | Виміряно | Вердикт |
|---------------|----------------------|----------|---------|
| prologue-операнд: `P[e+1] ∈ {DPL 0x82, DPH 0x83, ACC 0xE0}` → fn-start у `e` | ~12.7 | **3** | нижче порога |
| epilogue-driven: `P[kc] ∈ {RET 0x22, RETI 0x32}` → fn-start у `kc+1` | ~8.4 | **4** | нижче порога |

**Обидва напрями — НИЖЧЕ випадкового baseline** → сигналу нема. Причина структурна: **~58% відомих
плейнтекст-байтів = `0xFF`** (решітка), тож відомі стовпці просто **не семплюють** кодові байти, потрібні
патернам (розподіл: `0xff`:208, `0x02`:21, далі hex-ASCII криба); жоден із кандидатів не має незалежно
відомого сусіда для валідації, а `0xE0` (PUSH-ACC-операнд) трапляється лише 2× серед усіх відомих
стовпців. Це **вимір**, узгоджений із раніше вичерпаними методами (decode-forward floor-29,
relative-scan 21.5% noise-floor). **Маска лишається 111/514.** Не фабрикувати ці збіги як байти (пастка §4).

## 4. Чому решта маски **не** відновлюється з файлів (точна причина, коригує §9)

Наївний «консенсус стертих сторінок» дає позірно 513/514 стовпців при порозі ≥0.5, і навіть
version-split там «узгоджується». **Це пастка:** «стерті» сторінки насправді — кілька **дубльованих**
сторінок з тією самою 68-байтовою структурою даних; на не-stride стовпцях їхня мода = **значення даних**,
а не 0xFF. Тому `K = data − 0xFF` там **неправильна**, а узгодженість version-split виникає бо це той
самий спільний відкритий текст (не незалежні дані).

Емпіричне підтвердження хибності: розшифрування консенсусним `K` (513 стовпців) дає
**ентропію 7.116** (замість <5 для 8051-коду), **0 crib-збігів** (`Uosc`,`VSW`,`VNM`,`BOOT`,`1.2`…),
лише ~175–208 друкованих символів з 514 — тобто **шум**. Правильні лише 64 stride-стовпці
(на них розшифрування дає 0xFF, узгоджено). **Не існує повністю стертого сектора** (строго перевірено —
див. §5.0a), тож єдиної сторінки-криба у файлах немає.

**Формальний висновок:** решта ~450 стовпців — це стовпці **без відомого якоря** (щільний код/дані).
За теоремою §2 вони інформаційно не відновлювані з наявних 180 шифротекстів. Мовно-модельна атака
(8051-опкоди, біграми) також не працює на цій глибині — підтверджено §9.5 (2 і 3 версії: ентропія
падає лише до 7.26, 0 crib). Потрібно ≈8–16 версій; опубліковано лише 3.

> **Підсумок частини «file-only»:** практичний висновок §9 стоїть (повне розшифрування з файлів
> недосяжне), але **причина уточнена й кількісно оцінена**: відновлювані рівно **anchored-стовпці**
> (64 шт., 8051-структурна 0xFF-решітка), а не 37, як оцінювалось раніше.

## 5. Замикання задачі: **одна відома сторінка → вся маска** (математично тривіально)

Нехай є **одна** сторінка з відомим відкритим текстом `P*` (514 байтів) і її шифротекст `C*` (будь-який
сектор будь-якої версії — маска спільна). Тоді для **кожного** `i`:

```
K[i] = (C*[i] − P*[i]) mod 256          (точно, детерміновано, без статистики)
```

Одна сторінка фіксує **всі 514** байтів маски → `ofw_crypto.py decrypt` розкриває всі три образи; далі
`repack` створює валідний `.ofw`. Тобто вся невизначеність задачі стискається до **добування одного
known-plaintext сектора**. Нижче — три способи його дістати, від найдешевшого концептуально до
найнадійнішого практично.

### 5.0a Чому НЕ можна взяти «стерту» сторінку з файлу як known-page — ПЕРЕВІРЕНО, НІ
Природна ідея: якщо сторінка повністю стерта (усі 512 байтів = `0xFF`), то `K[i]=C[i]−0xFF` дає **всю**
маску з неї однієї. Логіка **правильна**, але емпірично **жодна сторінка у 3 файлах не є повністю `0xFF`**.

Тест (K-free, `C_a−C_b=P_a−P_b`; повна перевірка на кодових сторінках):
- 33 «ff@lat»-сектори (0xFF на всіх 64 відомих стовпцях) утворюють лише **4 різні кластери** вмісту.
- Для кожного кластера прийняли гіпотезу «повністю 0xFF» → `K=C−0xFF` → розшифрували кодові сторінки:
  ентропія лишається **6.95–7.24** (для читабельного 8051 треба <5.5) і **0 crib-збігів** — а прошивка
  **гарантовано** містить ASCII-криби (`Uosc`,`VSW`,`VNM`,…, які пристрій віддає по OBEX). Отже жоден
  кластер не є істинним ключем → **жодна сторінка не є повністю стертою**.
- Non-stride стовпці **варіюються 448/448** серед «ff@lat»-сторінок → на жодному з них `0xFF` не є
  спільним значенням; консенсус-`K` теж дає шум (ентропія 7.18). Тому **union**-покриття = ті самі **64**.
- **Спроба «підставити регулярні FF» ширше — ПЕРЕВІРЕНО, НІ** (2026-07-15): period-8 самоподібність
  «ff@lat» = лише **4.37%** (не повторюваний fill-патерн); усі 33 «ff@lat» збігаються рівно на **64**
  решіткових стовпцях (0 додаткових); кластери «ff@lat» різняться у **450/514** стовпців (K-free) →
  ці позиції provably **НЕ** FF. Отже понад **65** FF-based байтів (64 решітки + `K[1]`) додаткового
  ймовірного FF **немає**; будь-яка ширша FF-заливка суперечить даним. (Маску далі розширюють НЕ-FF
  методи — vector-opcode §3b, crib-drag §3d — до 106/514.)

**Висновок:** «ff@lat»-сторінки — це **структуровані сторінки даних** (8-байтові записи з `0xFF` на
offset 4), **а не стертий flash**. «ERASED» у ранній версії таблиці — оманливий ярлик (виправлено на
`ff@lat`). Стерта сторінка з файлу дала б **лише ті самі 64 байти**, не розширює маску. Стеля **FF-based**
відновлення — **64/514**; загальну file-only стелю НЕ-FF методи підняли до **107/514** (opcode §3b + §3f, crib §3d).
Повна (514) маска потребувала б known-page ззовні — але C2-readback **заблоковано** (§5.1). *(Приклад: 1.23
сторінка @0x6E00 (idx 53) — «ff@lat», але як повна маска дає ентропію 7.64 = чистий шум.)*

### 5.1 Спосіб А — C2 flash-дамп ⚠️ **READBACK ЗАБЛОКОВАНО** (уточнено користувачем 2026-07-15)
Silicon Labs C2 debug adapter (EC2/EC3/U-EC6/ToolStick або DIY `x893/C2.Flash`) *теоретично* читає одну
flash-сторінку = `P*`. **АЛЕ:** на цьому пристрої **security-lock ВСТАНОВЛЕНО, C2-readback вимкнено**
(підтверджено користувачем). Тому простий дамп **НЕ працює** — потрібен **glitch-bypass** блокування
(`C8051F34x_Glitch`, деталі `firmware_update_method.spike.md` §5/§8): апаратно складно, ризиковано
(можливий brick), **успіх не гарантований**. Отже це **вже НЕ «рекомендований дешевий» шлях**, а
інвазивний останній засіб. **Наслідок:** нема жодного *неінвазивного* способу дістати known-page →
**повна детермінована маска (514) недосяжна без glitch**; практичний максимум — **file-only структурна
атака** (§3, §3f) + опційно **більше версій** прошивки (яких немає). Див. оновлений §6.

### 5.2 Спосіб B — **тестова прошивка як оракул** (ідея користувача) — аналіз здійсненності
Bootloader — це **оракул розшифрування** `D_K(C) = C − K`, що пише результат у flash і **запускає** його.
Це дає спокусу chosen-plaintext атаки. Строгий розбір:

- **Парадокс завантаження (bootstrap).** Щоб залити *свій відомий* відкритий текст `P*`, треба надіслати
  `C* = P* + K` — а для цього вже потрібна `K`. Без `K` не можна закодувати робочу програму. **Оракул
  розшифрування сам по собі не породжує known-plaintext без каналу зчитування результату.**
- **Канал зчитування.** Якщо результат можна прочитати (C2-read після заливки, або якщо залита програма
  сама рапортує пам'ять по OBEX) — тоді `P*` відомий → `K = C* − P*`. Але зчитування знову впирається в
  C2 (Спосіб А) або в уже-працюючу керовану firmware (парадокс вище).
- **Чи вистачить 64 відомих байтів, щоб «бутстрапнути» мінімальний dumper?** Ні: 64 відомі стовпці —
  це розріджена решітка offset≡4(mod8), **немає жодного суцільного відрізка ≥4 байтів**. Розмістити
  зв'язний 8051-код (навіть крихітний UART-dumper) на такій решітці неможливо. Отже суто-програмний
  chosen-plaintext оракул **заблокований**.
- **Реальна цінність тестової прошивки:** не оракул, а **(1) валідатор** і **(2) визначення структури**:
  - зібрати відому 8051-збірку (SDCC/Keil) з характерними маркерами (вектори `LJMP`, ASCII `Uosc/VSW`,
    відомі калібр-таблиці) → отримати **еталонний `P*`** очікуваної структури тіла сторінки;
  - якщо цю прошивку **один раз** залити й **зчитати** (через C2 у Способі А, або порівняти поведінку) —
    вона стає повним known-plaintext крибом і завершує `K`;
  - навіть без заливки — еталон дає **емпіричну модель відкритого тексту** (частоти опкодів,
    розкладка 8-байтових структур, положення 0xFF-padding), яка **посилює** стовпцеву атаку §2 на
    anchored-сусідніх стовпцях і **підтверджує семантику** stride-8 offset-4 (розділ 3.2).

  → Тестова прошивка **не обходить** потребу в одному фізичному known-page, але **робить його
  максимально інформативним** і слугує еталоном коректності `K`.

### 5.3 Спосіб C — прошивка з нуля (fallback, якщо декомпіляція не вдасться)
Написати робочу firmware з нуля (SDCC/Keil C51) і залити через **C2** — при цьому шифр `.ofw`
**стає нерелевантним** (C2 пише plaintext у flash, оминаючи bootloader-крипто). Ціна: реалізувати
ADC/аналог/OBEX-стек заново і **втратити стоковий bootloader** (відновлює лише виробник), тож
робити лише як останній засіб і на власний ризик. Проміжний варіант: C2-write власного коду при
збереженні bootloader, якщо readback не заблоковано.

### 5.4 Toolchain та референсні приклади (для тестової прошивки / аналізу структури)
**Збірка + аналіз структури НЕ потребують заліза** (залізо треба лише для заливки/дампу).
- **SDCC 4.5.0** — у Manjaro `extra` (`pacman -S sdcc`); має заголовок `C8051F340.h` (точний чіп),
  вільний. Емітить `.ihx→.hex/.bin` + лістинги `.asm/.rst` (структура видна одразу, без disassembly).
- **Keil C51** — **ймовірний оригінальний компілятор вендора** (SiLabs Simplicity Studio використовує
  Keil C51 «під капотом», вільний для C8051). Найкращий для **байт-порівнюваної** структури.
- **naken_asm** — 8051 disassembler (github mikeakohn/naken_asm) — для розбору *розшифрованого* образу.
- **ucsim/s51** (у складі SDCC) — симулятор.
- **Заливка (пізніше, залізо):** C2 (`ec2drv`, DIY `x893/C2.Flash`), glitch `debug-silicon/C8051F34x_Glitch`.

**Незашифровані приклади під цей чіп (для аналізу коду):**
- **SiLabs 8-bit SDK** `www.silabs.com/8bit-software` → `Examples\C8051F34x` — Keil-джерела під **точний**
  чіп (USB/ADC/UART/Blinky), незашифровані = **найкраще** джерело референс-структури.
- **shraken/gboot** — USB-bootloader + застосунки для C8051F3xx (F34x), app за bootloader = **та сама
  модель пам'яті**, що в Oscill (app не з 0x0000); є `.hex`.
- **merbanan/C8051F300_examples** (SDCC, сусідній F300), **cjacker/opensource-toolchain-8051** (blink),
  **github.com/SiliconLabs** (офіційні приклади).

**Що це дає для двох цілей користувача:**
- **Перша сторінка (app @0x0400):** будь-який Keil/SDCC-образ показує стандартну структуру — таблиця
  reset/interrupt-векторів (`LJMP` на 0x…+3/+0x0B/+0x13…), C-startup (`?C_STARTUP` / `__sdcc_gsinit`),
  далі `main`. Сильно порівнювано → дасть розпізнати першу сторінку вендора **після** розшифрування.
- **ff@lat сторінки (CRC=D3/F5, ×6 копій):** референс порівнюваний **слабко** — це vendor-specific
  ДАНІ (повторена 512-байтова таблиця; оскільки дубльована, це **реальні дані, а не 0xFF-fill**). Щоб
  ідентифікувати — потрібен реальний plaintext (маска ← known-page, C2). Тест-прошивка тут — лише
  §5.2-валідатор.

### 5.4a Референс зібрано (SDCC 4.5.0, 2026-07-15) — `firmware/reference/`
Зібрано **реалістичний** C8051F340-образ осцилографа (`ref.c` → ~1645 B, ~4 сторінки, без заліза):
ADC-тракт + буфер, OBEX-регістрова таблиця з **реальними** іменами (VSW/VSN/VNM/VHW/QS/TS/RS/M1/O1/AP/
RT/AVG) + коди 0x70/0xB1/0xF0/0xF1, калібр-таблиця (8-байтові записи), USB-дескриптор (SiLabs VID
0x10C4), sine-LUT, hex-encode, segment-freq-detect, 7 ISR. Підтверджено на **known-plaintext** образі:
1. **Таблиця векторів = крок 8 байтів** (reset `LJMP`; ISR-слоти @0x03+8·n) — **той самий 8-байтовий
   період**, що й stride-8 решітка маски вендора.
2. **8-байтові записи даних з 0xFF на offset 4** (калібр-таблиця: `00 04 00 00 FF 01 00 05 | …`)
   виглядають **точно** як `ff@lat` сторінки вендора → сильний доказ, що `ff@lat` (L=14–24) — **реальні
   таблиці даних** (напр. калібрування) із зарезервованим 0xFF-полем, а не стертий flash.
3. **Ентропія 6.77 біт/байт** (реальний код+дані) vs **7.98** у зашифрованого payload → коректний
   decrypt **мусить** знизити ентропію до ~5–6 і відкрити криби (це pass/fail-тест майбутньої маски).
4. Криби — ті самі рядки, що й у `.ofw`-заголовку: `Oscill.com oscilloscope`, `Uosc`, `1.26`, +
   імена регістрів; `strings` їх дістає (як і в реальній прошивці).
5. **Релокований варіант @0x0400** (`build0400.sh`) відтворює layout «app за bootloader»: таблиця
   векторів переїжджає на 0x0400 (reset `LJMP 0x046C`, Timer0 @0x040B `LJMP 0x04C8`, …) — прямий
   аналог логічної сторінки вендора L=0. Змінюється лише старший байт LJMP-цілі (`02 00 6c → 02 04 6c`),
   8-байтова структура ідентична. `ref0400_app.bin`: байт 0 == flash 0x0400.
Байт-точна відповідність вендору потребує його компілятора (**Keil C51**); SDCC-структура — сильний,
але не байт-ідентичний орієнтир. Деталі: `firmware/reference/STRUCTURE.md`.

## 5.5 Варіант 1 у дії: matcher побудовано + SDCC виключено (2026-07-15)

Ідея Варіанту 1: **Keil C51 runtime** (startup + бібліотека `?C?IMUL`/`?C?IDIV`/…) — **суцільний**
known-plaintext, байт-ідентичний для версії компілятора. Локалізувати шаблон у образі → `K` на
**десятках послідовних** стовпців (стрибок проти розсипу з 78).

Побудовано `firmware/reference/matcher.py` (+ `mask_lib.py`):
- 8051-декодер довжин інструкцій → шаблон (**опкоди FIXED, операнди WILDCARD**);
- ковзне вікно по стовпцях; `K=C−template` на FIXED-байтах; **валідація** проти 78 відомих `K` +
  опкод-валідність; крос-версійна ідентичність для стабільних рутин.

**Результати:**
- **Позитивний контроль:** вбудований (зашифрований *реальним* `K`) SDCC-startup знайдено точно
  (offset 40, 4/4 overlap) → matcher коректний.
- **Тест SDCC проти образу:** найкращий збіг лише **1/1** overlap (проти 4/4 у контролі) →
  **SDCC ВИКЛЮЧЕНО** як компілятор вендора → узгоджується з гіпотезою **Keil C51**.

**Обмеження валідації:** щільність відомих `K` розріджена (на той час 78/514 ≈ 1 на 8 у решітці), тож короткий
шаблон (startup) дає лише ~3-4 overlap-перевірки; **довгі бібліотечні рутини (100+ B) валідуються
значно сильніше** (більше перетинів з решіткою + опкод-валідність).

**Fallback-шаблони (реконструйовані опкод-скелети, без Keil) — ПРОБУВАНО, НІ (2026-07-15):**
`fallback.py` прогнав реконструйовані Keil-startup / XDATA-clear / RAM-clear + універсальні ISR-прологи
(PUSH ACC/PSW/full, bank-switch) — у т.ч. **таргетовано** на відновлені ISR-сторінки (з карти векторів).
Результат: **0 впевнених збігів** (поріг ≥3, для ISR ≥2 на конкретній сторінці). Причина: реконструкції
**не байт-точні** (реальні Keil-порядок/регістри/операнди інші), а розріджена решітка K вимагає точного
збігу fixed-байтів на offset-4-mod-8. **Висновок:** шорткати (реконструкції) недостатні; потрібні
**точні байти реального Keil**. Це НЕ спростовує Keil (на відміну від точного SDCC-тесту) — лише
показує, що без справжнього компілятора Варіант 1 не запустити.

**Реальний Варіант 1 ВИКОНАНО (2026-07-15): Keil C51 v8.12 під Wine — 0 збігів.**
Користувач надав Keil C51 v8.12. Виконано:
- C51.exe/A51.exe працюють під Wine (eval-режим: LST так, .obj ні — обійдено).
- З `STARTUP.A51` (A51-лістинг) отримано **точний** startup-скелет — він **збігся** з моєю реконструкцією
  (`78 7F E4 F6 D8 FD 75 81 xx 02` = KEIL_SMALL) → реконструкція була правильна.
- **`omf_match.py`**: власний OMF51-парсер витяг **байт-точні** рутини з `C51S/C51L/C51FPS/C51FPL.LIB`
  (200+ рутин; перевірено — декодуються коректно, `0xA4`=MUL у *MUL, закінчуються `0x22`=RET).
- Matcher **валідовано** (позитивний контроль: вбудована рутина знайдена, 42/42 overlap).
- **Результат: 0 збігів** у образі вендора — навіть довгі рутини (LMUL 80B, UIDIV 86B), що валідувалися б
  сильно, якби були присутні.

**Розширено: Keil v9.53 + максимальні шаблони (2026-07-15) — ВИСНОВОК: НЕ Keil.**
- Порівняння рутин **v8.12 vs v9.53**: `?C?IMUL/LMUL/UIDIV` **байт-ідентичні** → runtime Keil
  **стабільний між версіями** → версія — НЕ причина 0 збігів.
- **Максимальний шаблон** (усі ненульові байти = FIXED; 0x00 = relocatable-placeholder = wildcard):
  LMUL 79B → **79 fixed**, позитивний контроль = **18** решіткових overlap (промахнутись неможливо).
- Матч максимальних шаблонів (S/L/C/FPS/FPL, обидві версії) vs образ вендора: **0 збігів**.

**ВИСНОВОК (сильний):** якби вендор використав Keil C51 будь-якої версії, `?C?LMUL` знайшовся б із ~18
overlap. Його (і всіх 160+ рутин) **немає** → **вендор НЕ використовував Keil C51** (як і не SDCC —
§5.5 вище). Найімовірніше: **інший компілятор** (Raisonance/IAR) або **рукописний асемблер** (типово
для щільної 30KB-прошивки осцилографа 2009 р.). Template-matching компіляторного runtime (Варіант 1)
для цієї прошивки **не працює** — matchable C-runtime відсутній.

**Варіант 1 остаточно вичерпано.** Стеля Варіанту 1 (template-matching) — **78/514**; згодом crib-drag
(§3d) + LJMP-решітка (§3f) підняли file-only маску до **107/514**. Детерміноване замикання (повні 514)
потребувало б known-page (Варіант 2) — але **C2-readback заблоковано** (§5.1), тож і воно недосяжне без
glitch. Інфраструктура (`matcher.py`, `omf_match.py`, `mask_lib.py`) лишається для інших runtime.

### 5.5a IAR EW8051 6.5 (2026-07-15) — недоцільно тестувати
Користувач надав IAR EW8051 6.5 (Wine). Стан:
- `xlib`/`xar`/`a8051` працюють **без ліцензії** (можна лістити/діставати модулі, асемблювати);
  компілятор `icc8051` — **license-blocked**.
- Runtime — формат **UBROF (.r51)**, є й **асемблерні джерела** (`8051/src/lib/*.s51`).
- **Блокер:** щоб зібрати правильний варіант runtime, `iar_check_symbols.h` вимагає **5+ макросів
  конфігу** (`__CORE__`, `__CODE_MODEL__`, `__DATA_MODEL__`, `__CALLING_CONVENTION__`,
  `__NUMBER_OF_DPTRS__` + DPTR select/visibility). Точна конфігурація вендора **невідома** →
  комбінаторний перебір; + IAR має **низький пріор** (SiLabs штатно = Keil), а його код (banked
  far-calls + віртуальні регістри) складніший для матчингу.

### 5.5b IAR — ЛІЦЕНЗІЮ ВИРІШЕНО, повний тест (2026-07-15): 0 збігів
Ліцензію `icc8051` активовано. Виконано **повний compile+link** справжнім IAR:
- `icc8051 itest.c --core plain` → конфіг вендор-дефолт для C8051F340: **plain / near / small /

- Матч vs образ вендора: **0 збігів** — навіть `?US_DIV_MOD` (129 опкодів → ~16 решіткових overlap,
  якби була присутня). DLIB **не** змінює ці цілочислові helper-и (спільні з CLIB) — не тестувалось.

**ПІДСУМКОВИЙ ВИСНОВОК Варіанту 1:** протестовано дефолт-конфіги **всіх трьох** основних 8051-C-компіляторів:

(C2 known-page) — але **C2-readback заблоковано** (§5.1), тож і він недосяжний без glitch. **Реалістичний
максимум без glitch — file-only структурна атака** (§3, §3f, зараз 107/514).

## 6. Практичний план (оновлено: C2-readback заблоковано)

1. **Зафіксувати часткову маску** (готово) — `firmware/ks_partial.json`, **107/514** байтів із тиром
   `confidence` (66 proven + **13** vector-hi-conf [12 IRQ-опкоди + col133 post-table LJMP, §3f] + 28 crib-LUT).
   Найдешевша перевірка коректності майбутнього повного `K`. Низько-впевнені — `ks_conjectural.json`
   (вкл. INT1/v15/Tmr0/Tmr2 opcode-кандидати, §3f).
2. **Вичерпати file-only структуру L=0** (§3f, зроблено частково): повна LJMP-решітка дала +1 доведений
   + 4 кандидати. Потенціал +4 → **111/514**, якщо ззовні підтвердити, що всі unused-вектори — LJMP.
3. **known-page — ТІЛЬКИ через glitch-bypass** (Спосіб А + `C8051F34x_Glitch`, §5.1): readback залочено,
   простий C2-дамп не працює; glitch ризиковий, успіх не гарантований. Це **єдина** дія, що дала б 514/514,
   але вона **інвазивна й непевна** (вже не «дешева»).
4. `ofw_crypto.py recover <ofw> <known_page> ks.bin` → повна маска (лише якщо п.3 вдасться).
5. Якщо glitch недосяжний — прийняти **часткову маску** (107–111/514) як стелю, або Спосіб C (прошивка з
   нуля через C2-**write**, якщо запис не залочено — окремо від readback).

## Conclusion

**Вердикт:** `concluded`.

- **Q1 (модель/умови):** маска `K∈(ℤ/256)^514` — перевикористаний адитивний keystream (many-time pad,
  mod 256, період 514, без зчеплення). Стовпець `K[i]` відновлюється ciphertext-only **лише** за наявності
  **відомого якоря** у відкритому тексті стовпця (теорема §2); інакше це one-time pad — інформаційно
  невідновлюваний.
- **Q2 (регулярний шаблон):** два патерни-якорі — (1) **stride-8 offset≡4(mod8) решітка** з якорем
  **0xFF** (64 стовпці); (2) **SEQ-поле** (col1) = `(0x20·L) mod255` → known-plaintext → `K[1]=0x06`.
- **Q3 (скільки/що далі):** з файлів надійно відновлено **107/514 = 20.8%** маски: 66 proven
  (64 lattice + `K[1]` SEQ + `K[2]` reset) + **13 vector-hi-conf** (12 IRQ-опкоди + col133 post-table LJMP,
  §3f) + **28 crib-validated** (два hex-LUT, §3d); +4 structural-кандидати (§3f) у `ks_conjectural.json`
  (потенціал 111/514). Решта потребувала б **однієї known-plaintext сторінки** (`K=C−P`) — але
  **C2-readback ЗАБЛОКОВАНО** (§5.1), тож known-page недосяжна без ризикованого glitch. **Тестова прошивка**
  — валідатор структури, не оракул (bootstrap-парадокс, §5.2). Бонус SEQ: розкрито **справжню карту адрес**.

**Ключова корекція попередньої роботи:** (1) «file-only вичерпано, ~37 background-стовпців» → уточнено до
**107 перевалідованих байтів** (64 stride + `K[1]` + `K[2]` + 13 vector-LJMP + 28 hex-LUT crib) з точною
причиною межі, патерном stride-8, SEQ→адресація, crib-drag hex-LUT (§3d) і **повною LJMP-решіткою L=0**
(§3f). (2) **C2-readback ЗАБЛОКОВАНО** (уточнено користувачем) → «рекомендований C2-дамп» **відкликано**;
неінвазивна стеля = **file-only 107–111/514**; повна маска — лише через glitch-bypass (§5.1).
Vector-table FF-padding спростовано (§3c); neighbor-extension безрезультатний (§3e).

**Рекомендований наступний крок (оновлено — C2-readback заблоковано):** повна маска потребувала б
known-page, а C2-read залочено (§5.1) → без ризикованого glitch недосяжно. Тому: (1) прийняти **file-only
маску 107/514** (потенціал 111, §3f) як робочу стелю; (2) якщо потрібна повна — concept на **glitch-bypass**
C2-read (інвазивно, ризик brick) або **custom firmware з нуля** через C2-**write** (Спосіб C). Тестова
прошивка лишається валідатором структури.
